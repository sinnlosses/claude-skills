スキルの運用について3点相談し、次のように決めた。

## 1. `develop/` を廃して `docs/` に寄せるか → 寄せない（変更なし）

`develop/`（毎セッション書き換わる作業状態）と `docs/`（意図したときだけ書き換える人向けの
成果物）は可変性と読者が違う。アーカイブが `develop/` → `docs/history/` の一方通行である
という形も、置き場が分かれていることで表現できている。現状維持。タスクは不要。

## 2. `direction.md` に中身があると `/next-task` が止まる仕様を直す

今は `skills/next-task/SKILL.md` の手順1で、`develop/direction.md` に見出し行以外の中身が
あればタスクを1件も実行せず終了し、`/loop` がそれを「続行不要」として受け取る。
これは非対称で損している。止めて得るのは「覆るかもしれないタスク1件を無駄に実行せずに済む」
ことだけなのに、失うのは「READY な todo が全部止まる」こと。しかも止めた先で `direction.md`
は自動タスク化されない（分解は方針決めを含むので `/next-task` は代行しない設計）ので、
止めても止めなくてもユーザーが戻るまで誰も何もしない。

直したい挙動:

1. `develop/direction.md` に中身があっても `/next-task` は止めない。完了報告に
   「未タスク化の指示あり（N行）」を1行添えるだけにする
2. 止めるのは `READY` が0件になったとき。そこで初めて「進めるものが無く、未タスク化の指示が
   ある → `/plan-tasks` が先」と報告して終了する
3. `/loop` が「続行不要」を受け取るのは 2 のときだけ

直す場所は `skills/next-task/SKILL.md` の手順1と完了報告のフォーマット、および
`skills/task-workflow/WORKFLOW.md` の「指示メモ（`develop/direction.md`）」節。
`skills/setup-tasks/SKILL.md` の `PENDING:` の扱いも、この方針と矛盾しないか見直す。

## 3. `docs/` の共通ファイル（architecture.md など）を作る手順を分かりやすくする

置き場の決め方が4通り混在しているのが原因。`docs/history/*` は規約で固定、`CONTEXT.md` と
`docs/adr/` は domain-modeling が固定、一方でアーキテクチャ提案は
`skills/architecture-proposal/SKILL.md:149` が「リポジトリの慣習に従う」、調査メモは
`skills/research/SKILL.md:12` が「慣例があればそこ、無ければ適切と思う場所」と、後ろ2つが
その場のモデルの判断になっている。さらに `docs/` に何が居るかの索引がどこにも無い。

新しいスキルは作らず、`task-workflow` が既にやっている「正典を1箇所に置く」形を真似する:

1. **置き場を規約で固定する。** アーキテクチャ提案は `docs/architecture.md`、調査メモは
   `docs/research/<topic>.md` に固定し、「慣習に従う」をやめる。`docs/history/` と同じ扱いにする
2. **`docs/README.md` を索引にする。** `docs/` に何かを書いたスキルは、そこに1行足すことだけを
   守る。このリポジトリの `README.md` の「由来の一覧が索引」と同じ発想で、ズレは検証コマンド
   （`scripts/check_repo.py`）で落とせるようにできないか検討する
3. **育て方を梯子として1箇所に書く。** 「新規プロジェクトでは何も作らない（遅延作成）→
   構造で迷ったら `/architecture-proposal` → 用語がブレ始めたら `CONTEXT.md` → 覆すのが
   高くつく決定をしたら ADR」。置き場は `README.md` の「プロジェクト側に要るもの」節の隣。
   各スキルはそこをスキル名で参照する（絶対パスを埋めない）
