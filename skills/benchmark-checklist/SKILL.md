# 計測の数を報告する前に

計測の数は、律速を名指せて、繰り返して同じ向きに出て、本当に走った仕事を測ったものだけが主張になる。
7問のどれかに答えられないまま言うと、数は事実ではなく印象になる。「短くなった」と言う前に、
同じ負荷で並べた別の計測があるかを先に見る。

## 走らせる前に

1. **言うつもりの主張を1文で書く**: 「検証の経過が短くなった」「CPU が減った」のように、何と何を比べて何と言いたいのか。
2. **計測スクリプトが何を測り、何を無視するかを読む**: 時計を回す区間の外に、ウォームアップ・起動・後片付けが落ちていないか。
3. **負荷とコア数を見る**: コア数は macOS なら `sysctl -n hw.ncpu`、Linux なら `nproc`。負荷は `uptime` の平均。
   他の仕事が走っていて止められないなら、A と B を交互に走らせ、揺れがあることを報告に書く。

## 7問

### 1. なぜ倍にならないか（律速を名指す）

数が動かなかった・思ったほど動かなかったなら、何に律速されているかを言う。計測とは別の回で、
プロファイラを付けて見る（付けると遅くなるため、数を取る回には付けない）。
手元で打てるもの: プロセスごとの CPU は `top -l 2 -pid <PID> -stats pid,cpu,mem`（Linux は `top -b -n 2 -p <PID>`）、
Node は `node --cpu-prof`、Python は `py-spy record -o out.svg --pid <PID>`。
CPU が余っていて待ちが長いなら I/O か別プロセス待ち。負荷をかける側が律速になっていないかも見る。

### 2. 両側を本番と同じ設定で走らせたか

リリースビルド・本番と同じフラグ・同じ版・同じデータ・現実的なキャッシュの状態で、両側を走らせる。
片側が既定の設定のままなら、比べたのは実装ではなく設定。整えて測り直してから勝ち負けを言う。

### 3. 限界の計算を超えていないか

数が、コア数・帯域・変えた部分の所要時間から出る上限を超えていないかを計算で確かめる。
全体の 10% を占める部分を消しても、速くなるのは最大で約 11%（1 / 0.9）。上限を超えた数は、
狙った仕事以外を測っているしるし。

### 4. エラーと失敗を数えたか

失敗・非成功の応答・時間切れ・再試行の件数を数え、出力が正しいことも確かめる。
早く拒否した結果は「速くなった」ように見え、時間切れと再試行は遅い。数える口が無い計測は、数える行を足す。

### 5. 再現するか

A と B を交互に5回以上走らせ、中央値と範囲（最小〜最大）で言う。順番に偏りが出ないように ABAB…と回す。
差が回ごとの揺れより小さいなら「差は測れない」。僅差の判定は順位和検定（Mann-Whitney の U 検定）を使う。

### 6. 全体の何% か

利用者が待つ経路の全体（現実的なデータの大きさ・並行度）で測り、部分の改善は全体に対する割合で言う。
部分で 2 倍になっても、全体の 3% なら全体は 1.5% しか動かない。

### 7. 本当に走ったか

時計を回した区間の中で、仕事が実際に行われたことを確かめる。リクエストがサーバに届いたか、行が書かれたか、
バイトが読まれたか、結果が使われたか。遅延評価や時間切れは、走っていない仕事の数を出す。

## 報告の形

- **判定を先頭に**: 速い・遅い・差なし・判定不能のどれか。
- **数は、数＋単位＋回数＋範囲＋律速で言う**: 例「中央値 38.2 秒（5 回交互、36.9〜40.1 秒）。CPU は 4 コア中 1 コアで頭打ち」。
- **判定不能にする**: 差があると言うのに律速を名指せない・片側が整っていない・4 と 7 を確かめていないときは、
  判定不能と書き、足りないものを名指す。
- PR や報告の本文には主たる数を 1 つだけ置き、各回の値と根拠は別の置き場に分ける。

## 1回でよいとき

利用者が「だいたいでよい」と頼んだ計測は 1 回でよい。ただし 4（エラー）と 7（本当に走ったか）は見て、
「1 回の計測」と報告に書く。選択肢を比べる計測は「だいたい」にしない。
