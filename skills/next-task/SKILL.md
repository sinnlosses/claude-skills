タスクを1サイクルぶん前に進めて終わる（全件進めたいときは `/loop /next-task`。続行/停止は `/loop` が
決める）。ルールは `task-workflow` スキルの `WORKFLOW.md`（以下「正典」）。`tw` は
`task-workflow` のタスク運用のコマンド（正典「`tw` コマンドの参照」）。
**`tw` の代わりに台帳やタスクファイルを手で操作しない。**

## このプロジェクトの設定（設定ファイル AGENTS.md → CLAUDE.md の「## タスク運用」節）

!`r=$(git rev-parse --show-toplevel 2>/dev/null); n=; for f in AGENTS.md CLAUDE.md; do [ -n "$r" ] && [ -f "$r/$f" ] && s=$(sed -n '/^## タスク運用/,/^## /p' "$r/$f" | grep .) && [ -n "$s" ] && { n=$f; break; }; done; if [ -n "$n" ]; then echo "（$n から読んだ）"; echo "$s"; else echo '（「## タスク運用」節が無い。AGENTS.md・CLAUDE.md の他の節に書かれた検証コマンドを探す。無ければ /setup-tasks で節を用意する）'; fi`

節に `- タスクの置き場: beads` があれば **Beads 方式**（正典「Beads 方式」）で、下の手順の
「Beads 方式では」の注記に読み替える（行が無ければファイル方式で、注記は飛ばす）。Beads 方式でトラッカーが
`github` なら、タスクID は Issue 番号の `GH-<n>` のことがある（`tw status` の1列目の形のまま使い、下の
`T-xxx` とコミットの件名の `T-xxx:` をそう読み替える）。
以下の**検証コマンド**・**整形コマンド**はこの節の値に読み替える。`なし` なら打たず、`## 完了条件`
だけで受け入れを判定してその旨を報告に書く。節が無くても「なし」と決めつけない（AGENTS.md・CLAUDE.md の
別の節に「変更後は必ず〜を通す」とあることが多い）。

## 手順

0. **依存を確かめる**: `command -v tw` が何も返さなければ、`tw` が PATH に張られていないとして
   `MISSING` を報告して終了する（`task-workflow` を含めて `./install.sh` を打ち直すよう案内する）。

1. **見渡す**: `tw status`（Beads 方式でトラッカーが `jira`・`github` なら、先に `tw sync` で取り込む。
   `TRACKER\tFAILED` は報告に添えて先へ進む）。終了コードで分かれる:

   | 終了コード | すること |
   | --- | --- |
   | 5 `LEGACY` | **旧形式**。「このプロジェクトは `develop/tasks.json` の旧形式。正典「旧形式からの移行」の手順で、`main` を出している作業ツリーから `tw migrate --dry-run` を打って移す（全作業ツリーの手を止めてから。スキルは移さない）」と案内して終了する |
   | 6 `MISSING` | タスク運用を始めていない。`/setup-tasks` を案内して終了する |
   | 1・3 | エラー出力か `INVALID` の理由をそのまま報告して終了する（直しに行かない） |

   あわせて `develop/direction.md` の `## ユーザーから` の行数を見る（手順3で使う。報告には写さない。
   節見出しの無い古いファイルは全体を `## ユーザーから` とみなす）:

   ```bash
   awk '/^## ユーザーから/{f=1;next} /^## /{f=0} f' develop/direction.md | grep -cv '^\s*$'
   ```

2. **取り残しを見る**: 行の `着手可否` が `CLAIMED` で、印の列の作業ツリー名が自分
   （`basename "$(git rev-parse --show-toplevel)"`）なら、前のセッションが途中で落ちている。
   着手せず、ID と「`tw release T-xxx` で捨てる／作業ツリーを見て人が続ける」の2択を添えて
   終了する（正典「status と着手の印」）。`stale` 行の他人の印は触らない（片付けるのは人）。

3. **選ぶ**: `着手可否` が `READY` の行から1件。**`/loop` から回っているときは `loopable: N` を
   選ばない**（ユーザーが直接呼んだときは選んでよく、着手前に判断の要る点を確かめる）。**`HOLD` は
   `/loop` からは選ばない。** ユーザーが直接呼んだときは、ユーザーが ID か「hold を」と指したとき、
   または `READY` が無いときに、依存がすべて解決済み（正典「status と着手の印」）の `HOLD` を選んでよい
   （選んだら手順3aへ）。候補が無ければ、この順に試す:
   1. `## ユーザーから` に中身がある → `plan-tasks` スキルの手順を**ファイル入口の分だけ**行う
      （`/loop` からでもよい。会話入口とドラフト（`develop/draft/`）には触らない）
   2. 登録したら `tw status` を取り直してこの手順3をやり直す。それでも無ければ、
      「進められるタスクが無い」と、残りの `HOLD`（人の判断待ち）と `N` の ID を添えて終了する

3a. **`HOLD` を決める**（手順3で `HOLD` を選んだときだけ。**委譲せずメインで行う**。サブエージェントは
   ユーザーに聞けないので、決める人がすり替わる）:
   1. `## 解くべき論点` と `## 注意` を読み、判断の材料を集める。調べもの（コード・文書・記録を
      読むこと）は委譲してよいが、案を選ぶところは渡さない
   2. `AskUserQuestion` で決めてもらう（推す案があれば先頭に置く）。決まらなければ何も書かずに
      「判断待ちのまま」と論点を添えて終了する（`hold` のまま残す）
   3. 決まったら、`status: hold` を `status: todo` に直し、答えを
      `## 決まっていること（蒸し返さない）` に日付と「ユーザー決定」を添えて書く（「なし」なら
      置き換える）。このファイルだけを `T-xxx: 判断を焼く` の件名で
      コミットし、`tw ship` で送る（正典「送り出し」。`hold` の切り替えのコミットも同じ `ship`）。
      **Beads 方式では**、`tw show T-xxx` の本文に答えを書き足して
      `tw edit T-xxx --status todo --body-file -` で渡す（コミットも `ship` も要らない）
   4. 手順4へ進む（決めた答えが本文にあるので、ここからは通常のタスクと同じく委譲してよい）。
      「やらない」と決まったときも同じく `todo` に戻し、手順4の `claim` のあと手順7で `--dropped` にする

4. **着手の印を立てる**: `tw claim T-xxx`。

   | 出力 | すること |
   | --- | --- |
   | `CLAIMED` | 次へ（手順5の前に `tw plan-check T-xxx` を打つ）。`branch=` が作業する枝 |
   | `TAKEN`・`NOT_READY` | 先を越された・状態が変わった。手順1から別の1件を選び直す（3回続いたら止まる） |
   | `DIRTY` | 作業ツリーに未コミットの変更がある。`git status --short` を添えて終了する（捨てない） |
   | `UNSHIPPED` | 主ブランチに入っていない自分のコミットがある（前のサイクルが送れていない）。`git log --oneline <主ブランチ>..HEAD`（枝名は `main` 固定ではない。正典「ファイル配置と設定ファイル（AGENTS.md → CLAUDE.md の順）」）を添えて終了する |
   | `INVALID` | 理由をそのまま報告して終了する |

4a. **作業ツリーを確かめる**: 検証コマンドの実行に要るもの（依存のインストール済みバイナリなど）と、
   組み立て済みの成果物が揃っているかをメインが確かめる（何を見るかはプロジェクトの CLAUDE.md の
   立ち上げの記述に従う）。無ければ委譲せず、人に立ち上げを頼んで `tw release T-xxx` する。

5. **委譲する（1回目: 計画）**: 先に、手順4のあとに打った `tw plan-check T-xxx` で分かれる
   （登録時に `## やること` を書いたか。正典「タスクファイル」）:

   | 出力 | すること |
   | --- | --- |
   | `PLAN_REGISTERED\tT-xxx\t<SHA>` | 登録時に書いた `## やること` が名指すファイルは変わっていない。1回目の委譲を省き、手順5cの「宛先が解決しないなど再開できなければ」の枝と同じやり方で新しい Agent を立て、実装させる（依頼文は手順5のうち「今回は実装しない…」の項目を除いたものと、「`## やること` は登録時に書いてある。`tw show T-xxx` で読んでそのとおり実装する」と、手順5cの依頼文） |
   | `PLAN_STALE\tT-xxx\t<変わったファイル>` | 名指したファイルが登録のあとに変わった。下のとおり委譲する（2回に分けるか、「1回にまとめて委譲するとき」）。依頼文に「登録時の `## やること` は古い（変わったファイル: <行の3列目>）。いまの主ブランチで調べ直して丸ごと書き直す」を足す |
   | `PLAN_NOT_FIRST\tT-xxx\tmissing` | 登録時に書いていない。下のとおり委譲する |

   原則は2回に分ける（下の「1回にまとめて委譲するとき」を除く）。
   1回目は `## やること` を書いて返すだけで、実装はさせない。メインが手順5bで返りを見てから、
   手順5cで実装させる。

   **メインが書いてよいとき**: 同じセッションでこのタスクの設計を利用者と決めていて、
   `## やること` に要る正典・コードをメインがすでに読んでいるときだけ、1回目の委譲を省いて
   メインが自分で `## やること` を書く（メインが新たに読み込みに行くなら、これまでどおり委譲する。
   メインの文脈を膨らませない）。書いたら中身だけを
   `tw edit T-xxx --section 'やること' --body-file -` で渡し、手順5bの表の見方を自分の計画に当てて確かめる
   （`tw plan-check T-xxx` が `PLAN_FIRST` を返し、`## やること` が `## 完了条件` の各行を覆って
   いるか。足りなければ自分で `tw edit` を書き直してから先へ進む）。確かめたら手順5cへ進む。
   1回目のエージェントがいないので、手順5cの「宛先が解決しないなど再開できなければ」の枝と
   同じやり方で新しい Agent を立てる（委譲先に渡す言葉を手順5・5cの依頼文と揃えるのはこの
   再利用で満たす）。

   **1回にまとめて委譲するとき**: `difficulty` が `haiku` か `sonnet` で、かつ `## 完了条件` が
   コードに触れない（文書・`SKILL.md` などの文面だけを直す）ときは、計画と実装を1回の委譲で頼む
   （メインが `## やること` を読んで実装を指示し直す1ターンと、往復の待ちを省く）。
   「メインが書いてよいとき」に当たるならそちらが先で、書いたあとの委譲は手順5cのとおり。
   渡す言葉は、次の「それ以外は委譲する」の依頼文のうち「今回は実装しない…」の項目を下の2項目に
   替え、手順5cの依頼文（`tw verify`・`CONFLICT`・後段に手を付けない・`## 結果` を書かない・
   draft の形・friction log・コメント規約・完了条件ごとの報告）を足して、1回で渡す:
   - 「**先に `tw edit T-xxx --section 'やること' --body-file -` で `## やること` を書いてから実装する**
     （節の中身だけを渡し、`## やること` の見出しの行は付けない。`### 1. …` の形で実行の順に番号を振った段で書き、完了条件の各行を
     どの段のどのファイルのどこをどう直して満たすかまで書く。合図の `n/N` の N は段の数にそろえる。
     `## やること` を `tw edit` で書くまでの合図は、`n/N` を入れずに `状況 | 計画 | 何をした・何が分かった` で送る。
     描画を変えるタスクでは、組み立てた直後に画を撮ってメインの目視を受ける段を、E2E の期待値を
     撮り直す段と `tw verify` の段より前に置く。
     作業ツリーが変わったあとの初回の記入は `WORK_BEFORE_PLAN` で拒まれるので、読むだけの調べを
     先に済ませてから書く）。書いたあとは `## やること` のとおり実装する。判断が想定より要ると
     分かったら押し切らず、そこで止めて報告する。`## 目的・背景`・`## 完了条件` は変えない
     （変えると `FRAME_CHANGED` で拒まれる。`--change-frame` は付けず、変えたい理由を報告する）」
   - 「**前提が崩れていて作業が要らないと分かったら、作業せずに止まって**、`dropped` にすべき理由を
     報告する（`## やること` は書かなくてよい）。`## 目的・背景` の主張が実物と違っていたら直さず
     『前提が誤り』と報告する」

   文書の担当は並べて起こさない（メインが `## やること` を読む前に動き出すため。1匹で通す）。
   手順5cの「文書の担当が完了した」を待つ項目も渡さない。途中で `difficulty` を上げる、または
   完了条件がコードに触れると分かったときは、前の担当を `TaskStop` で止め、2回に分けて委譲し直す。

   **それ以外は委譲する**: Agent ツールで `difficulty` と同じモデルのサブエージェントへ（メインのモデルは
   判断材料にしない。一致していても委譲する。正典「difficulty とモデルの切り替え」）。
   `subagent_type` は、Agent ツールの説明に並ぶエージェント一覧に `no-delegate`（`tools` から
   `Agent` を外したエージェント定義。claude-skills の `agents/no-delegate.md` を `install.sh` が
   `~/.claude/agents/` へ張ったもの）があればそれを使う。一覧に無ければ、`install.sh` を打つ前
   （人がやること）とみなして、これまでどおり `general-purpose` を使う。`no-delegate` は、着手の印が
   立った作業ツリーでのコミットを hook（`tw commit-guard`）で拒む定義でもある。`general-purpose` に
   落ちたときは拒む仕組みが無く、手順6の `COMMITS_SINCE_CLAIM` だけが頼りになる。
   本文は貼らず、次を渡す（`retrospect` の SKILL.md を指す箇所は
   `${CLAUDE_SKILL_DIR}/../retrospect/SKILL.md` を解決した絶対パスに置き換えて渡す。委譲先は
   `${CLAUDE_SKILL_DIR}` を持たない）:
   - タスクID とファイルのパス（`develop/task/T-xxx.md`）。「まずそれを読む。書き足すときはファイルを
     直に書き換えず、節の中身だけを `tw edit T-xxx --section '<節名>' --body-file -` に渡す」。
     **Beads 方式では** パスの代わりに「`tw show T-xxx` で読み、書き足すときは節の中身だけを
     `tw edit T-xxx --section '<節名>' --body-file -` に渡す」
   - 「**今回は実装しない。いまのコードで前提を調べ直して `## やること` の中身を書き、`tw edit` で渡して、
     そこで報告して止まる**（見出しは登録時から枠にある。空か「なし」を置き換える。`tw edit` が、
     そのとき作業が始まっていたかを記録する。渡すのは `## やること` の中身だけ）。
     `## やること` は、`### 1. …` の形で実行の順に番号を振った段で書き、完了条件の各行を
     どの段のどのファイルのどこをどう直して満たすかまで書く。
     進み具合の合図は `状況 | 計画 | 何をした・何が分かった` の形で送り、`n/N` を入れない
     （`n/N` は `## やること` の段の番号と数のときだけ使う）。
     描画を変えるタスクでは、組み立てた直後に画を撮ってメインの目視を受ける段を、E2E の期待値を
     撮り直す段と `tw verify` の段より前に置く。
     調べるために読むだけで、ファイルは変えない。作業ツリーが変わったあとの初回の記入は書き込まれずに
     `WORK_BEFORE_PLAN` で拒まれる。そのときは `--after-work` を付けずに、作業をしてしまったことを
     報告して止まる。前提が崩れていて作業が要らないと分かったら、
     作業せず `dropped` にすべき理由を報告する」
   - 「`## 目的・背景` がファイルの存在・パス・行番号を主張していたら、`## やること` を書く前に実物で
     確かめる（別のリポジトリのファイルなら、そのリポジトリの実物を見る）。違っていたら直さず『前提が誤り』と報告する」
   - 「本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開いて読み、`## やること` を見本と
     食い違わないように書く」
   - 「`develop/task/T-xxx.md` 以外の `develop/` を触らない。コミットしない
     （`git add -A` もしない。着手の印が立った作業ツリーでコミットしようとすると拒まれる。拒まれたら
     回避せず、コミットせずに報告で返す）。`tw show`・`tw edit` のほかの `tw` コマンドは打たない」
   - 「`git stash` を使わない（stash の山は作業ツリーの間で共有され、別のセッションの退避を
     取り違える）。変更の前後を見比べるなら一時コミットか `git show HEAD:<path>` で見る」
   - 「グローバルへのリンク（例: パッケージマネージャのグローバルリンク）・ホームのファイル・グローバル設定を
     触らない。必要なら報告に書く」
   - 「外部に捨てる資源（リポジトリ・Project など）を作る前に、`gh auth status` のスコープで
     消せることを確かめる。消せなければ作らずに、人にスコープの追加を頼む」
   - 「`/` やホーム全体を `find` で探さない」（置き場の見当が付く所だけ探す。
     ルートから探すと上限で背景に回り、報告のあとも走り続ける）
   - 「待つコマンドには必ず上限を付ける（回数か、スクリプトの中の待ちの timeout か、
     シェルを呼ぶツールの timeout 引数。`timeout` コマンドは環境に無いことがある）。背景のコマンドの完了を待ったまま手番を終えない。撮影などが
     終わらなければ止めて、そのことを報告に書く」
   - 「背景で起こしたコマンド（テスト・サーバ・watch）は、報告の前に止める」（残ると同じ作業ツリーで
     受け入れの検証コマンドが返らなくなる）
   - `general-purpose` に委譲したときだけ渡す（`no-delegate` は `Agent` ツール自体が無く
     仕組みで立てられないので渡さない）: 「サブエージェントの中では別のエージェント
     （fork を含む）を立てず、レーンを順に自分で読む」

   `loopable: N` のタスク（ユーザーが直接呼んだとき）は委譲せずメインで行う（`## やること` を作業より
   先に `tw edit --section 'やること'` で書くのは委譲先と同じ。`tw edit`・`tw verify` の関門も同じく掛かる）。着手して初めて
   ユーザーの判断が要ると分かったら、front matter を `loopable: N` に直し、`tw release T-xxx`
   して預ける（直した1行は手順7と同じ形でコミットして `tw ship`。Beads 方式では
   `tw edit T-xxx --loopable N` と `tw release T-xxx` だけで、コミットは要らない）。判断が重いと分かったら
   `difficulty` を上げてから委譲し直す。委譲し直すときは、前の担当を `TaskStop` で止めてから
   新しい担当を立てる（`SendMessage` で呼び戻さない）。

5b. **返りを見る**（2回に分けたときは1回目の返り。1回にまとめたときは、表の下の「1回にまとめたとき」を読む。委譲先の hand-back か、Agent ツールの完了の通知が届いてから。
   `SendMessage` の途中経過の `完了` の合図だけでは届いたとみなさない（委譲先が合図の
   直後に hand-back を返して止まり、合図だけを見て送った5cが届かないことがある）。通知が「背景の作業を待っている」なら
   手順5aの1）。`tw plan-check T-xxx` と `git status --short`（タスク自身を除く差分の有無）を打ち、
   `tw show T-xxx` の `## やること` を読む:

   | 見たもの | すること |
   | --- | --- |
   | 「前提が誤り」の報告 | 2回目に進まない。手順7で `--dropped` にするか、`## 目的・背景` を直して手順4から着手し直すかを決める（直す `tw edit` には `--change-frame` を付ける。付けないと `FRAME_CHANGED` で拒まれる） |
   | `dropped` にすべき理由の報告 | 2回目に進まず、手順7へ（`--dropped`。理由を結果に書く） |
   | `PLAN_FIRST`・差分なし・`## やること` が `## 完了条件` の各行を覆う | 手順5cへ |
   | `PLAN_FIRST`・差分なし・完了条件の行が抜けている、または読んで「どこをどう直すか」が分からない | 2回目に進まず、足りない点を `SendMessage` で伝えて1回目をやり直させる（`tw edit` で書き直させる。差し戻しは1回まで。もう一度足りなければメインが `tw edit` で直して5cへ） |
   | `PLAN_NOT_FIRST\tT-xxx\tmissing` | `## やること` を書かずに返した。`SendMessage` で書かせる（差し戻しは1回まで） |
   | `PLAN_STALE\tT-xxx\t<変わったファイル>` | 登録時の古い `## やること` を書き直さずに返した。`missing` と同じく `SendMessage` で書き直させる（差し戻しは1回まで） |
   | `PLAN_NOT_FIRST\tT-xxx\tafter-work`・`unrecorded`、または差分あり | 1回目に実装した。差分が `## やること` と合うなら活かして手順5cを飛ばして手順6へ、合わなければ差分を退けて（自分の作業ツリー内の `git restore`）5cへ。どちらでも理由の語を一言メモしておく（手順6aの兆候「受け入れのときにメインが直したもの」。札は `制約違反`） |
   | `NOT_OWNER` | 自分の作業ツリーの印が無い（人が `tw release --force` した、など）。ID を添えて終了する |

   **1回にまとめたとき**: 実装まで済んでいるので差分があるのが普通で、上の表の「差分なし」「差分あり」の
   行は当てはめない。次を見る。
   - `tw plan-check T-xxx` が `PLAN_FIRST`（`## やること` を作業より先に `tw edit` で書いた。
     登録時に書いた計画で進めたときの `PLAN_REGISTERED` も同じに読む）で、
     `tw show` の `## やること` が `## 完了条件` の各行を覆っていること。差分は `## やること` と
     合うかを手順6で読む
   - 「前提が誤り」「`dropped` にすべき」の報告なら、表のとおり手順7か手順4へ。2回に分けて頼み直さない
   - `PLAN_NOT_FIRST`（`missing`・`after-work`・`unrecorded`）か `PLAN_STALE` なら、`## やること` を作業より先に書かなかった。
     理由の語を一言メモしておく（手順6aの兆候「受け入れのときにメインが直したもの」。札は `制約違反`）。
     差分が完了条件を満たすなら活かして手順6へ進み、`## やること` はメインが差分から書き起こして
     `tw edit T-xxx --section 'やること' --after-work` で渡す。満たさなければ差分を退けて（`git restore`）2回に分けて頼み直す
   - `NOT_OWNER` は表のとおり

5c. **委譲する（2回目: 実装）**: 1回目のエージェントへ `SendMessage`（`to` は Agent ツールの結果の
   名前か `agentId`）で続ける。完了していても、名前は使え、送ると transcript から再開する
   （調べた文脈が引き継がれ、背景で走り、完了の通知が届くのは1回目と同じ。手順5aもそのまま掛かる）。
   宛先が解決しないなど再開できなければ、手順5と同じ設定の新しい Agent に、手順5の依頼文と
   「`## やること` は書いてある。`tw show T-xxx` で読んでそのとおり実装する」を渡す。
   モデルは1回目と同じ `difficulty` のモデル（`difficulty` を上げるときだけ、前の担当を
   `TaskStop` で止めて新しい Agent を立てる）。次を渡す（`retrospect` の SKILL.md を指す箇所は
   手順5と同じく絶対パスにする）:
   - 「`## やること` のとおり実装する。判断が想定より要ると分かったら押し切らず、そこで止めて報告する」
   - 「検証コマンドは `tw verify` で打って通す（打つ前に主ブランチを取り込み、取り込んだら先頭に
     `FOLDED` が出る。通ると作業ツリーの中身の鍵が控えられ、受け入れで中身が同じなら検証を省ける。
     落ちたら `VERIFY_NOT_PASSED` とログのパスが出る）。検証コマンド（check の全段）は `tw verify`
     以外で打たない（対象を絞った単体テスト・E2E のファイル単位の実行は打ってよい）。`CONFLICT` が出たら解かずに、衝突した
     ファイルを添えて報告して止まる。通したあとにファイルを変えたら打ち直す。`tw show`・`tw edit`・`tw verify` のほかの `tw` コマンドは打たない」
   - 作業先が別のリポジトリのときだけ渡す（下の手順6の「作業先が別のリポジトリのとき」）: 「作業先の
     リポジトリでは、別の作業ツリー（`git worktree add -b <枝> <パス> main`）で直してコミットし、**コミットの
     あと**にその作業ツリーを cwd にして `tw verify` を打つ（控えは cwd の作業ツリーごとで、鍵に `HEAD` の
     SHA を含むので、コミットの前に打つと受け入れで `NOT_VERIFIED head` になる）。**`main` へ入れず、
     作業ツリーと枝を消さずに残して**、作業ツリーのパスと `tw verify` の判定行（`VERIFIED`・
     `VERIFY_NOT_PASSED` など）を報告に書く。作業先に `tw` の台帳が無く `tw verify` が `MISSING` を
     返すときは、検証コマンドを自分で打って通し、打ったコマンドと終了コードを報告に書く」。
     別のリポジトリの作業ツリーには着手の控えが無いので、そこでのコミットは hook に拒まれない
   - 文書の担当を並べて起こしたときだけ渡す（下の「文書の担当を並べて起こすとき」）: 「文書の担当が
     別に動いている。メインから『文書の担当が完了した』と伝えられるまで、`tw verify` はまだ打たない
     （それ以外の実装は進めてよい）」
   - 「完了条件が後段のタスクの本文を直す・分けるよう求めていても、後段には手を付けず申し送りだけ
     書く（本文の編集と `tw new` での分割はメインが受け入れで行う）」
   - 「タスクファイルに `## 結果` の節を書かない（`tw done` が書く）」
   - 「`develop/draft/` にドラフトを積むときは、ドラフトの形（太字の見出し1行・`根拠`・`出し先` の
     子項目）で書く」
   - 「気になった点は終わってから思い出す自由記述ではなく、作業中に気づいた時点で
     `<retrospect の SKILL.md の絶対パス>` の節「札と1行の書式」の1行（`- <色> <札>: <何が起きたか>
     （<根拠の場所>）`）で friction log として書き留め、報告に載せる。検証コマンドやテストが
     1回落ちて、打ち直したら通ったときも `揺れ` の札で書く。何も起きなければ
     「friction log: なし」と書く」（行が無ければ書き忘れ、`なし` と書いてあれば確認済みで
     何も無かった、と区別する。打ち直して通った揺れは、書かないと受け入れで見えない。
     1回目の間に気づいた点もここで載せる）
   - 「新しく書くコメントは、プロジェクトの規約（CLAUDE.md など）があればそれに従い、呼ぶ側・前例のファイル名・正典の
     要約と参照を並べない。前例のファイルのコメントの量を手本にしない。『〜のは、…ため』の
     ような方針・理由の説明も足さない」
   - 「報告では `## 完了条件` の各行について、満たしたか・何で確かめたかを1行ずつ書く。見た目や
     設定を変えたら、実際に効いたことを実物で確かめる」
   - 「本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開き、作った画面と見比べる。
     食い違ったら見本に合わせ、見比べた結果を報告に1行書く」
   - 「完了条件に目視（画面・見た目）があるタスクでは、撮った画像のパス（幅ごとに1行。いちばん狭い
     幅がどれかも書く）を報告に書く。画像は作業ツリーの外の、受け入れまで消えない場所に置く」
   - 「描画を変えるタスクでは、部品を差し替えて組み立てた直後に画を撮り、E2E の期待値の撮り直しと
     `tw verify` の前に、画像のパスを書いた『目視待ち』の報告を返して止まる。メインが `SendMessage` で
     承認を返してから、期待値の撮り直しと `tw verify` に進む。差し戻されたら直して撮り直し、もう一度
     『目視待ち』で返す」

   **文書の担当を並べて起こすとき**: `## やること` に文書の直し先と中身（ファイルパスと直す内容）が
   書いてあり、実装の担当と触るファイルが重ならないときだけ、実装の委譲（上）と同時に、文書の直し
   専用の Agent を1体、`sonnet` 固定で並べて起こす（同時に足すのは1匹まで。実装の担当と合わせて2匹）。
   触るファイルが分けられなければ並べず、これまでどおり1匹にまとめる。`subagent_type` の選び方は
   実装の担当と同じ（一覧に `no-delegate` があればそれ、無ければ `general-purpose`）。

   本文は貼らず、タスクIDと `## やること` に書かれた文書のパスを渡し、次を渡す:
   - 「`## やること` に書かれた文書だけを直す。触ってよいファイルはそれだけで、実装のファイル・
     `develop/`・グローバル設定・ホームのファイルには触らない」
   - 「走らせてよいコマンドは文書の検査（そのプロジェクトの迷子の参照の検査・整形）だけ。
     build・E2E・check 全段のような重いコマンドは走らせない。検証コマンドは実装の担当の
     `tw verify` の1回に寄せるので、ここでは打たない」
   - 「`tw` コマンドは `tw show T-xxx` だけ（`tw edit`・`tw verify` など他は打たない）」
   - 「コミットしない（`git add -A` もしない。着手の印が立った作業ツリーでコミットしようとすると拒まれる。
     拒まれたら回避せず、コミットせずに報告で返す）。`git stash` を使わない」
   - グローバルへのリンク・ホームのファイルを触らない、外部に捨てる資源を作らない、`/` やホーム
     全体を `find` で探さない、待つコマンドに上限を付ける、背景で起こしたコマンドは報告の前に
     止める、を渡す（実装の担当と同じ諸注意）
   - `general-purpose` に委譲したときだけ渡す: 「サブエージェントの中では別のエージェントを立てない」

   文書の担当の完了（hand-back か、Agent ツールの完了の通知。届いたと見なす基準は手順5bと同じ）が
   届いたら、その差分に目を通してから、実装の担当へ `SendMessage` で「文書の担当が完了した」と
   伝える。文書の担当の差分も、実装の担当の差分と合わせて手順6でメインが読む。

5a. **委譲先の無応答に対応する**（手順5（1回にまとめたときを含む）・5cで投げたあと、報告が来ないまま長く止まったとき。文書の
   担当を並べて起こしたときは、実装の担当・文書の担当それぞれに独立して当てはめる。片方が完了して
   いても、もう片方の無応答は別に扱う）:
   1. **完了の通知が「背景の作業を待っている」で届いたら、待たずにその場で作業ツリーと成果物を見る**
      （通知を受けても放置し、人が指摘するまで気づかなかった実績がある）。
   2. **最後の書き込みから30分ほど動きが無ければ、作業ツリーに手を出さずに止める**（目安であって
      厳密な計測を求めない。進捗を尋ねても返らなかった実績が2件あるので、尋ねる段は必須にしない）。
   3. 止めたら最後の状態と `git diff` を読み、**完了条件を満たしていれば手順6で受け入れる**。
   4. 途中なら、済んだことと残りを明示して**別のサブエージェントに引き継ぐ**。`tw release` で
      捨てるのは差分が使えないときだけ。

6. **受け入れる**: 作業ツリーを直し始める前に、委譲先の `完了 | N/N` の合図か hand-back が届いていることを
   確かめる（文書の担当を並べて起こしたときは、実装の担当と文書の担当の両方について確かめる）。
   届いていなければ `TaskStop` か `SendMessage` で止めてから触る。報告をそのまま信用しない。

   **目視待ちの報告が来たとき**（描画を変えるタスクで、委譲先が組み立てた直後に返したもの。完了の
   hand-back ではないので、ここで受け入れを始めない）: 報告の画像を最低1枚（いちばん狭い幅）`Read` で
   開き、`## 完了条件` の目視の行と見比べる。合っていれば `SendMessage` で承認を返し（委譲先は期待値の
   撮り直しと `tw verify` に進む）、合っていなければ何がどう違うかを返して差し戻す。差し戻したときは
   一言メモしておく（手順6aの兆候「受け入れのときにメインが直したもの」。報告と画が違ったなら札は
   `自己申告の不正確さ`）。

   **完了条件に目視（画面・見た目）があるとき**: 委譲先が報告した画像のうち最低1枚（いちばん狭い幅）を
   `Read` で開き、`## 完了条件` の目視の行と1行ずつ見比べる。**見比べるまで手順7の `tw done` に進まない。**
   報告にパスが無い・開けない（置き場の一時ディレクトリが消えた、など）なら `SendMessage` で撮り直させる。
   報告の文字（「3幅とも一致・はみ出し 0px」など）だけで受け入れない。開いたパスは手順7の `## 結果` に書く。

   `## やること` は手順5bで見たので（手順5で `PLAN_REGISTERED` だったときは、登録時に書いた計画をそのまま使った。
   ここで `tw plan-check T-xxx` を打てば同じ `PLAN_REGISTERED` が返り、`PLAN_FIRST` と同じに読む）、ここでは `git diff` を読み、整形コマンド → `tw verify-check` を打つ
   （下の表。検証を省くか `tw verify` で打つかを決める）。方針からズレた実装はその場で直す。
   作業ツリーを cwd にした残りのプロセスが無いかを `ps` で見て、あれば止める。
   **検証コマンドが1回で通らず、打ち直したら通った**ときは、落ちた・打ち直した・通った、を
   一言メモしておく（手順6aで `retrospect` の兆候「運良く助かった」に使う。委譲先の friction log の
   `揺れ` の行も同じく扱う。受け入れで検証を省いたときは、それが唯一の手がかり）。
   **人が止めた・直させた・やり直させた**ときも、そのことだけを一言メモしておく（手順6aの兆候
   「人の差し戻し」。人の発言は写さない）。

   | `tw verify-check` の出力 | すること |
   | --- | --- |
   | `VERIFIED_SAME\t<木の SHA>` | 検証コマンドを打たずに次へ（委譲先が `tw verify` で通した中身と、整形のあとの中身が同じ） |
   | `NOT_VERIFIED\t<理由>` | `tw verify` を打つ（`none`＝委譲先が控えていない・最後の検証が落ちた／`base`＝委譲先が控えたあとに主ブランチが進んだ。`tw verify` が取り込んでから打つ／`content`＝整形や受け入れの直しで中身が変わった／`head`／`command`）。`VERIFIED`・`VERIFIED_UNSTAMPED` は通った（取り込んだときは先頭に `FOLDED` の行）。`CONFLICT` なら取り込みが衝突した（何も書き換えず、検証コマンドは打っていない）。手順8の `CONFLICT` と同じく、衝突したファイルを添えて人に預けて終了する。`VERIFY_NOT_PASSED` なら出力の末尾とログを読んで直し、打ち直す。`PLAN_MISSING`（`## やること` が空のまま作業がある。手順5bを通っていれば出ない）なら、差分から中身を書き起こして `tw edit T-xxx --after-work` で渡してから打ち直す |
   | `NOTHING` | 検証コマンドが無い。完了条件を目視で確かめる |

   **作業先が別のリポジトリのとき**（タスクが直す対象が自分の作業ツリーの外のリポジトリ）: 控えは
   cwd の作業ツリーごとに別なので、`git diff` と `tw verify-check` は、委譲先が残した作業先の作業ツリー
   （報告のパス）で `cd <パス> && tw verify-check` と打つ（自分の作業ツリーで打つと `NOT_VERIFIED none`
   になるだけ）。表は同じに読む。`VERIFIED_SAME` なら、検証コマンドを打たずに作業先の本体で
   `git merge --ff-only <枝>` して、作業ツリーと枝を消す（`git worktree remove`・`git branch -d`）。
   `NOT_VERIFIED` ならその作業ツリーで `tw verify` を打ち直してから同じ段取りへ進む。受け入れで直すなら
   その作業ツリーで直してコミットしてから打つ。`tw` が `MISSING` を返す作業先では控えが無いので、
   委譲先の報告を信用せず検証コマンドを打つ。

   受け入れで作業ツリーを直したら、`tw verify-check` から打ち直す。`tw ship` が付け替えたときの
   検証は、この控えでは省かれない（付け替えが起きるのは、受け入れのあとに主ブランチが進んだときだけ）。

   手順7で `tw done` を打ったときの出力に `COMMITS_SINCE_CLAIM` の行が続いたら、次のとおり
   扱ってから先へ進む（`claim` した時点より後に、委譲先が hook（`tw commit-guard`）をすり抜けて作った
   コミットがあった合図。すり抜けるのは `general-purpose` への委譲と、Bash の文字列に `git` が出ない
   コミットだけ。ファイル方式・Beads 方式のどちらも同じ形。控えの無い古い印では出ない）:

   | 出力 | すること |
   | --- | --- |
   | `COMMITS_SINCE_CLAIM` が無い | 次へ（`claim` の後に委譲先がコミットしていない） |
   | `COMMITS_SINCE_CLAIM\tT-xxx\t<sha,…>` | `git show <sha>` で中身を見る。「コミットしない」の指示に反した委譲先のコミットなら、この手順6の「人の差し戻し」と同じくメモを残し、打ち消す（`git revert`）か中身ごと活かすかを決めてから手順7のコミットへ進む |

6a. **振り返る**（`/loop` から回っているときも。委譲せずメインで行う）: `retrospect` スキルの
   `SKILL.md`（`${CLAUDE_SKILL_DIR}/../retrospect/SKILL.md`）の節「1件だけ振り返る」**だけ**を読んで
   従う。兆候に当たったときだけ `develop/draft/` にドラフトのファイルを足し、
   どちらでも `## 結果` に入れる `- 振り返り:` の1行を決める。

7. **完了にしてコミットする**: `## 結果`（正典「結果の書き方と知見の置き場」。3行程度、自分の
   コミットのハッシュは書かない）を標準入力で渡す:

   ```bash
   tw done T-xxx --result-file - <<'EOF'
   - 検証コマンド: 1204 pass / 0 fail（+9）
   - 振り返り: 兆候なし
   EOF
   ```

   完了条件に目視があったときは `- 目視: <開いた画像のパス> を <完了条件の行> と見比べた` の1行を足す。

   `dropped` にするときは `--dropped` を付け、理由を結果に書く。**Beads 方式では**、`DONE` は
   stage せず（`## 結果` は Beads の comment に入る）、コミットは作業のファイルと（積んだなら）
   ドラフトのファイルだけ。差分が無ければコミットせずに手順8へ進む（`tw ship` が `NOTHING` を
   返して閉じる）。ファイル方式では、`DONE` が出たら、**コミットの前に
   もう一度整形コマンドを打つ**（`タスク運用`節が `なし` なら不要。`tw done` が書き込んだ結果の
   表は手順6で打った分より後にできるので、そのままだと整形コマンドの検査が付け替え後に落ちる）。
   打ったら作業のファイルを**個別に** `git add` し（`git add -A` は使わない）、タスクファイル
   （再整形して改めて `git add` し直す）、手順6aで積んだならドラフトのファイルと一緒に
   **1コミット**にする。件名は `T-xxx: <何をしたか>`
   （正典「コミットメッセージ」）、末尾の署名も同じ節に従う。知見は
   `## 結果`・`## 注意`・正典の docs・新しいタスクへ置き、`develop/progress.md` には書かない。

7a. **振り返り済みのタスクファイルを消す**: `tw prune`（`/loop` から回っているときも）。
   消せるものが10件に届くまでは `NOTHING` で何もしないので、削除のコミットは10件ごとに1つになる。
   Beads 方式では常に `NOTHING`。

   | 出力 | すること |
   | --- | --- |
   | `PRUNED` | `git rm` 済みで stage されている。**タスクのコミットとは別の1コミット**にする。件名は `振り返り済みのタスクファイルを消す（N件）` で、**タスクIDを置かない**（複数タスクをまとめて消す1コミットだから）。いま完了にしたタスクは印があるので消えず、次の回で消える |
   | `NOTHING` | 消すものが無いか、まだ10件に届かない。次へ |
   | `DIRTY` | 手順7のコミットに入れ損ねた変更がある。`git status --short` を添えて終了する（捨てない） |
   | `INVALID` | 理由をそのまま報告して終了する（手順7のコミットは送らずに残る） |

8. **送る**: `tw ship`（手順7aのコミットも一緒に送る）。

   | 出力 | すること |
   | --- | --- |
   | `SHIPPED` | 完了。`kept=feature/T-xxx` が付いていたら、枝を消せなかったことを報告して人に預ける（消さない）。Beads 方式で続く行に `NOT_CLOSED`・`TRACKER\tFAILED`・`BACKUP\tFAILED` があれば、行を添えて報告する（送れてはいる。`TRACKER` は `tw sync` で打ち直せる） |
   | `NOTHING` | 送るコミットが無い。Beads 方式で作業の差分が無かったときはこれで閉じている（`SHIPPED` と同じく完了として扱う）。ファイル方式では手順7のコミットを入れ損ねているので、`git status --short` を添えて終了する |
   | `MAIN_DIRTY`・`DIRTY` | 本体（か自分）が汚れている。パスを添えて終了する（`main` は動いていない） |
   | `CONFLICT` | 衝突したファイルを添えて人に預ける（`resolving-merge-conflicts` スキルで解ける） |
   | `VERIFY_FAILED` | 付け替え後の検証が落ちた。出力の末尾を添えて人に預ける（送っていない） |
   | `RACE` | 3回先を越された。人に預ける |

   どれで止まっても `/loop` は「続行不要」と扱う。push はしない。

## 完了報告のフォーマット

報告は**人が読むためのもの**で、`/loop` のための行を並べない。`/loop` の続行判断は、同じ会話に
残っているツールの結果（`tw ship` の先頭語と、送ったあとに取り直す `tw status`）から行う。

1. **結論を1文目に置く**: 送れたときは「`T-xxx <summary>` を完了して main へ送りました。」
   （`dropped` なら「`T-xxx <summary>` を見送って（dropped）main へ送りました。」と理由を1文）。
   `SHIPPED` の範囲・`branch=`・コミットのハッシュは書かない。手順8より前で止まったとき
   （`VERIFY_FAILED`・`CONFLICT`・`DIRTY`・取り残し・進められるタスクが無い、など）は、止まった
   ことと先頭語を結論にし、各手順の表が「添える」としたもの（パス・衝突したファイル・出力の末尾）を続ける
2. **何をしたか**を3項目程度の箇条書きで。変えたものと、それで何ができるようになったか・何が
   直ったかを1項目ずつ（ファイルの一覧やコマンドの経過ではなく中身を言う）
3. **人に知らせること**があるときだけ: 受け入れで直したこと、残した判断や気になった点（手順6aでドラフトに積んだかを添える）、
   手順3でタスク化したなら登録したタスクID、`kept=` で枝を消せなかったこと
4. 検証コマンドの結果（件数。「なし」なら完了条件を目視で確かめたこと。完了条件に目視があれば、開いた画像と見比べた結果も）と、手順6aの振り返り
   （`## 結果` に入れた `- 振り返り:` の行そのまま）を1行ずつ
5. `/loop` で進められる行（取り直した `tw status` で `着手可否` が `READY` かつ `loopable` が `Y`）が
   無くなったときだけ1行: 未完了が残っていなければ「全タスク完了」、`HOLD`・`loopable: N` が
   残っていれば、その ID を添えて「残りは人の判断待ち」

書かないもの: 結論と重なる「完了したタスク」の行、手順7aで消したタスクファイルの件数、
`tw status` の件数、`develop/direction.md` の行数、`stale`・`legacy_progress` の行
（これらは `tw status` を打てば人も見られる）。

**`/loop` の続行判断**（報告ではなく、会話に残ったツールの結果で決める）: `tw ship` が `SHIPPED`
以外、または手順8より前で終了したなら続行しない。`SHIPPED` なら送ったあとに `tw status` を
取り直し、`着手可否` が `READY` かつ `loopable` が `Y` の行があるか、`## ユーザーから` に中身があれば
続行し、どちらも無ければ続行しない。
