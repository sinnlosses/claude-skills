タスクを1サイクルぶん前に進めて終わる（全件進めたいときは `/loop /next-task`。続行/停止は `/loop` が
決める）。ルールは `task-workflow` スキルの `WORKFLOW.md`（以下「正典」）。以下の `task` は
`python3 ${CLAUDE_SKILL_DIR}/../task-workflow/scripts/task.py` の略。**`task` の代わりに台帳や
タスクファイルを手で操作しない。**

## このプロジェクトの設定（CLAUDE.md の「## タスク運用」節）

!`sed -n '/^## タスク運用/,/^## /p' CLAUDE.md 2>/dev/null | grep . || echo '（「## タスク運用」節が無い。CLAUDE.md の他の節に書かれた検証コマンドを探す。無ければ /setup-tasks で節を用意する）'`

以下の**検証コマンド**・**整形コマンド**はこの節の値に読み替える。`なし` なら打たず、`## 完了条件`
だけで受け入れを判定してその旨を報告に書く。節が無くても「なし」と決めつけない（CLAUDE.md の
別の節に「変更後は必ず〜を通す」とあることが多い）。

## 手順

1. **見渡す**: `task status`。終了コードで分かれる:

   | 終了コード | すること |
   | --- | --- |
   | 5 `LEGACY` | **旧形式**。「このプロジェクトは `develop/tasks.json` の旧形式。正典「旧形式からの移行」の手順で、`main` を出している作業ツリーから `task migrate --dry-run` を打って移す（全作業ツリーの手を止めてから。スキルは移さない）」と案内して終了する |
   | 6 `MISSING` | タスク運用を始めていない。`/setup-tasks` を案内して終了する |
   | 1・3 | エラー出力か `INVALID` の理由をそのまま報告して終了する（直しに行かない） |

   あわせて `develop/direction.md` の `## ユーザーから`・`## エージェントのドラフト` の行数を見る
   （報告に使う。節見出しの無い古いファイルは全体を `## ユーザーから` とみなす）:

   ```bash
   awk '/^## ユーザーから/{f=1;next} /^## /{f=0} f' develop/direction.md | grep -cv '^\s*$'
   awk '/^## エージェントのドラフト/{f=1;next} /^## /{f=0} f' develop/direction.md | grep -cv '^\s*$'
   ```

2. **取り残しを見る**: 行の `着手可否` が `CLAIMED` で、印の列の作業ツリー名が自分
   （`basename "$(git rev-parse --show-toplevel)"`）なら、前のセッションが途中で落ちている。
   着手せず、ID と「`task release T-xxx` で捨てる／作業ツリーを見て人が続ける」の2択を添えて
   終了する（正典「status と着手の印」）。`stale` 行の他人の印は報告に添えるだけで触らない。

3. **選ぶ**: `着手可否` が `READY` の行から1件。**`/loop` から回っているときは `loopable: N` を
   選ばない**（ユーザーが直接呼んだときは選んでよく、着手前に判断の要る点を確かめる）。`HOLD` は
   どの場合も選ばない。候補が無ければ、この順に試す:
   1. `## ユーザーから` に中身がある → `plan-tasks` スキルの手順を**ファイル入口の分だけ**行う
      （`/loop` からでもよい。会話入口と `## エージェントのドラフト` には触らない）
   2. 登録したら `task status` を取り直してこの手順3をやり直す。それでも無ければ、
      「進められるタスクが無い」と、残りの `HOLD`（人の判断待ち）と `N` の ID を添えて終了する

4. **着手の印を立てる**: `task claim T-xxx`。

   | 出力 | すること |
   | --- | --- |
   | `CLAIMED` | 次へ。`branch=` が作業する枝 |
   | `TAKEN`・`NOT_READY` | 先を越された・状態が変わった。手順1から別の1件を選び直す（3回続いたら止まる） |
   | `DIRTY` | 作業ツリーに未コミットの変更がある。`git status --short` を添えて終了する（捨てない） |
   | `UNSHIPPED` | `main` に入っていない自分のコミットがある（前のサイクルが送れていない）。`git log --oneline main..HEAD` を添えて終了する |
   | `INVALID` | 理由をそのまま報告して終了する |

5. **委譲する**: Agent ツールで `difficulty` と同じモデルのサブエージェントへ（メインのモデルは
   判断材料にしない。一致していても委譲する。正典「difficulty とモデルの切り替え」）。
   本文は貼らず、次を渡す:
   - タスクID とファイルのパス（`develop/task/T-xxx.md`）。「まずそれを読む」
   - 「**最初に、いまのコードで前提を調べ直して `## やること` を本文に書き足す**（置く位置は
     `## 注意` の前。節の並びは正典「タスクファイル」）。前提が崩れていて作業が要らないと分かったら、
     作業せず `dropped` にすべき理由を報告する」
   - 検証コマンドを通すこと。「`develop/task/T-xxx.md` 以外の `develop/` を触らない。コミットしない
     （`git add -A` もしない）。`task` コマンドは打たない」

   `loopable: N` のタスク（ユーザーが直接呼んだとき）は委譲せずメインで行う。着手して初めて
   ユーザーの判断が要ると分かったら、front matter を `loopable: N` に直し、`task release T-xxx`
   して預ける（直した1行は手順7と同じ形でコミットして `task ship`）。判断が重いと分かったら
   `difficulty` を上げてから委譲し直す。

6. **受け入れる**: 報告をそのまま信用しない。`git diff` を読み、`## やること` が書き足されている
   ことを確かめ、整形コマンド → 検証コマンドを打つ。方針からズレた実装はその場で直す。

7. **完了にしてコミットする**: `## 結果`（正典「結果の書き方と知見の置き場」。3行程度、自分の
   コミットのハッシュは書かない）を標準入力で渡す:

   ```bash
   task done T-xxx --result-file - <<'EOF'
   - 検証コマンド: 1204 pass / 0 fail（+9）
   EOF
   ```

   `dropped` にするときは `--dropped` を付け、理由を結果に書く。`DONE` が出たら、作業のファイルを
   **個別に** `git add` し（`git add -A` は使わない）、タスクファイル（stage 済み）と一緒に
   **1コミット**にする。件名は `T-xxx: <何をしたか>`（正典「コミットメッセージ」）、末尾は
   セッションの attribution の指示に従う。知見は `## 結果`・`## 注意`・正典の docs・新しいタスクへ
   置き、`develop/progress.md` には書かない。

8. **送る**: `task ship`。

   | 出力 | すること |
   | --- | --- |
   | `SHIPPED` | 完了。行末の `branch=` を報告に写す。`kept=feature/T-xxx` が付いていたら、枝を消せなかったことを報告して人に預ける（消さない） |
   | `MAIN_DIRTY`・`DIRTY` | 本体（か自分）が汚れている。パスを添えて終了する（`main` は動いていない） |
   | `CONFLICT` | 衝突したファイルを添えて人に預ける（`resolving-merge-conflicts` スキルで解ける） |
   | `VERIFY_FAILED` | 付け替え後の検証が落ちた。出力の末尾を添えて人に預ける（送っていない） |
   | `RACE` | 3回先を越された。人に預ける |

   どれで止まっても `/loop` は「続行不要」と扱う。push はしない。

## 完了報告のフォーマット

最後に次を1行ずつ示す（`/loop` が続行判断に使う）:

- done（または dropped）にしたタスクID と、`SHIPPED` の範囲と `branch=`
- 検証コマンドの結果（件数。「なし」なら完了条件を目視で確かめたこと）
- `task status` を取り直した `ready`（READY 件数）・`counts` の `hold` の件数と、
  `todo_loopable` の `N` の件数（0件なら「全タスク完了」と明言する）
- 手順3でタスク化したなら、登録したタスクID（そのコミットが完了のコミットとは別であること）
- `develop/direction.md` の `## ユーザーから` / `## エージェントのドラフト` の行数
- `stale`・`legacy_progress` の行が出ていれば、その内容（片付けるのは人）
