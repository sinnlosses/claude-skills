# コードベースアーキテクチャの改善

アーキテクチャ上の摩擦を洗い出し、**深化の機会（deepening opportunities）**を提案する: 浅いモジュールを深いモジュールに変えるリファクタリングである。目的はテスト容易性と AI によるナビゲーション性である。

このスキルはプロジェクトのドメインモデルに基づいて動き、共有された設計語彙の上に成り立つ:

- Skill ツールで `codebase-design` を呼び出し、アーキテクチャの語彙（**モジュール**・**インターフェース**・**深さ**・**シーム**・**アダプター**・**レバレッジ**・**局所性**）とその原則（削除テスト、「インターフェースがテストの表面である」、「アダプターが1つならそれは仮説上のシーム。アダプターが2つなら本物のシーム。」）を借りる。すべての提案でこれらの用語をそのまま使い、「コンポーネント」「サービス」「API」「境界」に流れないこと。
- `CONTEXT.md` のドメイン言語が良いシームに名前を与え、`docs/adr/` の ADR がこのスキルが再び争うべきでない決定事項を記録する。ユーザーが場所を指定したらそれに従う。

## 手順

### 1. 探索する

**スキャンする前に範囲を決める: YAGNI。** モジュールを深化させる効果は、そのモジュールへの将来の変更を楽にすることで生まれるので、最近変更された部分に重みを置く。どこを見るかを、見る前に決める:

- ユーザーが方向（モジュール、サブシステム、痛点）を指名していれば、それに従い、以下の推測はしない。
- そうでなければ、コミット履歴（`git log --oneline`）をある程度遡り、コードベースのホットスポット、繰り返し出てくるファイルや領域を見つけ、それらのパスに先に注意を向ける。変更が散らばっていて明確なホットスポットがなければ、網を広げる。

まず、触れる領域のプロジェクトのドメイン用語集（`CONTEXT.md`）と ADR を読む。

次にサブエージェントを立ち上げてコードベースを歩かせる。硬直したヒューリスティックに従うのではなく、有機的に探索し、摩擦を感じた場所を書き留める:

- 1つの概念を理解するために、多くの小さなモジュールを跳び回らなければならないのはどこか？
- モジュールが**浅く**、インターフェースが実装とほぼ同じ複雑さになっているのはどこか？
- テストしやすさのためだけに純粋関数が抽出されているが、本当のバグは呼び出し方に潜んでいる（**局所性**が無い）のはどこか？
- 密結合したモジュールがシームを越えて漏れているのはどこか？
- コードベースのどの部分が未テストか、または現在のインターフェースを通してテストしづらいか？

浅いと疑うものには**削除テスト**を当てる: それを削除したら複雑さは集約されるか、それとも単に移動するだけか？「集約される」という答えこそが求めている信号である。

### 2. 候補を HTML レポートとして示す

自己完結した HTML ファイルを OS の一時ディレクトリに書き、リポジトリには何も残さない。`$TMPDIR` から一時ディレクトリを解決し、無ければ `/tmp`（Windows では `%TEMP%`）にフォールバックし、`<tmpdir>/architecture-review-<timestamp>.html` に書く。実行ごとに新しいファイルになるようにする。ユーザーのために開き（Linux では `xdg-open <path>`、macOS では `open <path>`、Windows では `start <path>`）、絶対パスを伝える。

レポートはレイアウトとスタイルに **CDN 経由の Tailwind** を、構造をグラフ/フロー/シーケンスで確実に伝えられる図には **CDN 経由の Mermaid** を使う。Mermaid と手作りの CSS/SVG を混在させる: 関係がグラフ状のとき（呼び出しグラフ、依存関係、シーケンス）は Mermaid を、もっと編集的なものにしたいとき（マス図、断面図、collapse アニメーション）は手作りの div/SVG を使う。各候補には**before/after の視覚化**を付ける。視覚的であること。

各候補について、次を含むカードを描く:

- **Files**: 関係するファイル/モジュール
- **Problem**: 現在のアーキテクチャがなぜ摩擦を生んでいるか
- **Solution**: 何が変わるかの平易な説明
- **Benefits**: 局所性とレバレッジの観点、テストがどう改善するか
- **Before / After diagram**: 浅さと深化を示す、左右に並べた自作の図
- **Recommendation strength**: `Strong`・`Worth exploring`・`Speculative` のいずれか、バッジとして表示

レポートの最後に **Top recommendation** 節を置く: どの候補を最初に手掛けるべきか、その理由。

**ドメインには `CONTEXT.md` の語彙を、アーキテクチャには `codebase-design` の語彙を使う。** `CONTEXT.md` が「Order」を定義しているなら、「FooBarHandler」ではなく「Order サービス」でもなく、「Order intake モジュール」と話す。

**ADR との衝突**: 候補が既存の ADR と矛盾する場合、その摩擦が ADR を再検討するに値するほど本物であるときだけ表に出す。カード内に明示する（例: 警告のコールアウトで「ADR-0007 と矛盾するが、〜という理由で再考する価値がある」）。ADR が禁じている理論上のリファクタリングを片っ端から列挙しない。

HTML の雛形、図のパターン、スタイルの指針は [HTML-REPORT.md](HTML-REPORT.md) を参照。

まだインターフェースを提案しない。ファイルを書いたら、ユーザーに「どの候補を掘り下げますか？」と尋ねる。

### 3. grilling ループ

ユーザーが候補を選んだら、Skill ツールで `grilling` を呼び出し、決定木を一緒にたどる: 制約、依存関係、深化したモジュールの形、シームの裏に何を置くか、どのテストが生き残るか。

決定が固まるにつれて副作用はその場で起こす。Skill ツールで `domain-modeling` を呼び出し、ドメインモデルを最新の状態に保つ:

- **`CONTEXT.md` に無い概念にちなんで深化したモジュールに名前を付けたら？** その用語を `CONTEXT.md` に追加する。ファイルが無ければその場で作る。
- **会話の中で曖昧な用語を明確にしたら？** その場で `CONTEXT.md` を更新する。
- **ユーザーが実質的な理由でその候補を却下したら？** ADR を提案する形で申し出る: 「今後のアーキテクチャレビューが同じ提案を繰り返さないよう、ADR として記録しましょうか？」将来の探索者がその理由を実際に必要とするときだけ申し出て、その場限りの理由（「今はその価値がない」）や自明な理由は見送る。
- **深化したモジュールの代替インターフェースを探りたければ？** Skill ツールで `codebase-design` を呼び出し、その design-it-twice の並列サブエージェントのパターンを使う。
