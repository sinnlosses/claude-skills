# 変更が差分の外で壊すもの

差分は読める。壊れるのは、差分に映らない場所であることが多い。
呼び出し元を並べるのは grep で一瞬で済むので、成果にしない。時間は「この変更はなぜ安全か」を支える事実を確かめることに使う。

## いつ使う

- 小さい差分なのに、何かを壊しそうで信用できないとき
- 共有する型・関数・設定・保存形式を変えたとき
- マージ・送り出しの前に、差分の外の影響を確かめたいとき

差分の中の規約・仕様との一致は `code-review`、「通った」と言う前の証拠取りは `verifying-before-completion` に任せる。

## 安全な理由の1つの事実

「この変更は壊さない」と言える理由は、たどるとたいてい1〜2個の事実に集約される
（例: この値は常に非 null、この項目は古い読み手に無視される）。
呼び出し元の列挙だけを成果にしない。その事実を名指し、確かめることが仕事になる。

## 確信の5段

安全だと考える事実ごとに、どこまで確かめたかを言う。

1. **言った**: 根拠なく述べただけ
2. **行を指した**: ファイルと行を挙げた
3. **反例を潰した**: 壊れる経路を挙げ、1つずつ起きないことを追った
4. **実コードを走らせた**: 小さなスクリプトやテストで、その事実が成り立つ出力を得た
5. **実機で再現した**: 動いているアプリで、変更前後の振る舞いを見た

上げられなかった事実は「未証明」と書く。高い段に見せかけない。

## 手順

1. **変更を読む**: 差分が書いていない振る舞い（既定値・暗黙の順序・例外の握りつぶし）も含めて、何が変わるかを言う。
2. **安全な理由の1つの事実を見つける**: 「大丈夫そう」の理由をたどると、たいてい1〜2個の事実に集約される（例: この値は常に非 null、この項目は古い読み手に無視される）。それを名指す。
3. **grep が止まるところを読む**:
   - 読んでいるライブラリの実装と、固定されている版
   - 実行の順・タイミング・後始末
   - 保存・送信される形（JSON、スキーマ、ワイヤ形式）と、別の言語や古い版が同じバイト列を読む場合
   - feature flag と設定の組み合わせ
4. **残った危険を言う**: 起きやすさと、起きたときの被害の2つで書く。確認できたものと、消せたものを分ける。
5. **1つの事実を走らせて確かめる**: 小さなスクリプトかテストを書き、事実が成り立つ出力を得る。走らせられないなら、段2〜3までと書いて「未証明」にする。

## 返すもの

- **何が変わったか**: 1〜3文
- **安全な理由の1つの事実**: 事実、到達した確信の段、証拠（打ったコマンドと出力、または行）。上げられなければ「未証明」
- **危険**: 場所、起きやすさ、被害、確かめ方
- **確かめて消したもの**: 何を調べ、なぜ問題ないか
- **合流前に打つ最も安い確認**: コマンド1つ

呼び出し元の列挙だけを返さない。共有する前に、私的な情報（パス・認証情報・会話の中身）を取り除く。
