# 振り返り

タスクを1件やり終えるたびに得た「次はこうしたい」は、その場で言わないと消える。このスキルは
**まだ振り返っていないコミット範囲**を切り出し、材料を突き合わせて、**次に同じ状況が来たときに
振る舞いが変わるものだけ**を書き留める。

守ることが3つある。

1. **同じ範囲を二度振り返らない。** 振り返りは2つある。`/next-task` の中の**1件ごとの振り返り**
   （下の「1件だけ振り返る」）は、タスクファイルの `## 結果` の `- 振り返り:` の1行が印。手で呼ぶ
   **まとめての振り返り**（下の「手順」）は、`develop/retrospective.md` の先頭の1行が基準点で、
   ここを更新して初めて「振り返った」ことになる。まとめての振り返りは、印のあるタスクを飛ばす
2. **承認ゲートを通す。** 出力は `develop/draft/` にドラフトのファイルとして積む
   だけ。`docs/` も `CLAUDE.md` も `develop/task/` も直接は書き換えない（1件ごとの印は
   `/next-task` が `task done` の結果に入れる）。振り返りは
   「気づき」であって決定ではなく、正典を変えるかどうかはユーザーが決める
3. **会話の中身を写さない。** トランスクリプトから取るのはツール名・ファイルパス・
   コマンドの先頭2語・件数・時刻だけ。トランスクリプトには利用者と Claude の生の会話が
   入っているので、記録にもドラフトにも写さない（プロジェクトに会話内容の扱いの規約が
   あるなら、それが優先する）。`material.py` がこの線を引いているので、生の jsonl を
   自分で開かない

## 札と1行の書式

振り返りで拾う引っかかりには、下の**札**を1つと**色**を1つ付ける。札の語彙と書式はこの節にしか
書かない（兆候の表・ドラフト・`/next-task` の依頼文はここを指す）。何回目かを数えられるように、
語彙は増やさず、当てはまりが悪いときは一番近い札を選ぶ。

**札**（何のずれか。上の7つは開発者とエージェントのずれの分類 S1〜S7、下の3つはエージェントの外の摩擦）:

| 札 | 何が起きたか |
| --- | --- |
| `診断違い` | 原因の見立てが外れ、違う所を調べた・直した（S1） |
| `意図の読み違い` | 頼まれたことと違うものを作った・完了条件の読みがずれた（S2） |
| `制約違反` | 書かれている規約・手順・禁止事項に反した（S3） |
| `頼まれていない拡張` | 求められていない変更・機能・整理を足した（S4） |
| `実装の誤り` | やることは合っていたが、書いたものが間違っていた（S5） |
| `操作の誤り` | コマンド・ツールの使い方を誤った（引数・場所・順序）（S6） |
| `自己申告の不正確さ` | 報告・`## 結果` が実物と食い違った（済んでいないのに済んだ等）（S7） |
| `正典の不備` | タスク本文・正典・規約が実物とずれていた・要ることが書いていなかった |
| `揺れ` | 同じことをもう一度やると結果が変わった（打ち直して通った・単独なら通る） |
| `道具` | スクリプト・コマンド・環境が壊れていた・足りなかった（手で繰り返し書かされた、を含む） |

エージェント側の7つと外の3つの両方に当たるときは、**直す先が決まるほう**を選ぶ（規約が無くて
反した → `正典の不備`、規約があるのに反した → `制約違反`）。

**色**（どれだけ響いたか。札とは別の軸）:

| 色 | 目安 |
| --- | --- |
| `赤` | 止まった・人に預けた・壊れたまま先へ進みかけた（受け入れで落ちた・報告が実物と違った） |
| `黄` | 手間取ったが、その場で自分で戻せた |

「うまくいった」（緑）は書かない。次に振る舞いを変えないので、手順3の物差しで落ちる。
`赤` は1件でも手順3の物差しにかける。

**1件の1行**（作業中の書き留め・報告に載せるとき）:

```markdown
- <色> <札>: <何が起きたか（1文）>（<根拠の場所: ファイルパス・コマンドの先頭2語・節の名前>）
```

例: `- 黄 揺れ: 検証コマンドが1回落ち、打ち直すと通った（pnpm run check）`

根拠の場所に会話の中身（発言・返答の文）を写さない（上の「守ること」3）。

## 手順（まとめて振り返る。手で呼ぶ）

### 0. 依存を確かめる

`${CLAUDE_SKILL_DIR}/../task-workflow/scripts/task.py` が無ければ、`task-workflow` スキルが
張られていないとして `MISSING` を報告して終了する（`install.sh` で `task-workflow` も一緒に
張るよう案内する。以下の `task.py`・`scan.py`・`material.py` の呼び出しはこれが前提）。

### 1. 範囲を決める

先に形式を確かめる:

```bash
python3 ${CLAUDE_SKILL_DIR}/../task-workflow/scripts/task.py status > /dev/null; echo $?
```

`5`（`LEGACY`）なら「旧形式（`develop/tasks.json`）。`task-workflow` スキルの WORKFLOW.md
「旧形式からの移行」の手順で `task migrate --dry-run` から移す（このスキルは移さない）」と案内して
終了する。`6`（`MISSING`）はタスク運用を始めていないので `/setup-tasks` を案内して終了する。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/scan.py .
```

出力の読み方:

| 出力 | 意味 | すること |
| --- | --- | --- |
| `range` + コミットのTSV | 未振り返りの範囲がある | 手順2へ |
| `EMPTY\t<since>..<head>` | 前回から進んでいない | 「振り返る対象が無い」と報告して終了 |
| `MISSING` | `develop/retrospective.md` がまだ無い | 下の「初回」へ |
| `INVALID\t<path>\t<理由>` | 記録ファイルが読めない・ハッシュがリポジトリに無い | **データの不備**。理由をそのまま報告して終了（中身を確かめずに書き換えない） |
| 上のどれでもない出力 | `python3` が無い・スクリプトが落ちた | **環境の故障**。エラー出力を添えて報告して終了 |

TSVの列は `hash / 日付 / タスクID / ファイル数 / 増減 / 件名`。末尾に `commits`・`tasks`・
`reviewed`・`unmapped`（タスクIDの無いコミット）・`transcripts` が出る。

**振り返る単位はタスク**なので、`tasks` に並んだIDを対象にする。`reviewed` は1件ごとの振り返りが
済んだタスク（そのコミットの版の `## 結果` に `- 振り返り:` がある。Beads 方式では `## 結果` の comment）で、`tasks` から外してある。
材料を集め直さず、手順3で「複数のタスクで同じ手作業が出ている」を見るときに件名と diffstat だけ使う。`unmapped` のコミット
（アーカイブ・typo直し・依存更新）は数だけ見て、中身が気になるものがあるときだけ拾う。

**初回**（`MISSING`）: どこから振り返るかはユーザーに決めてもらう。`git log --oneline -20` を
見せて「ここから」を選んでもらい、選ばれたコミットの**1つ前**を起点にして記録ファイルを作る
（選んだコミット自身が範囲に入るように）。勝手に「最初のコミットから」にしない——
何十件も一度に振り返ると、どれも薄くなる。

### 2. 材料を集める

対象のタスク1件ずつに、次を実行する。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/material.py . T-XXX --diff
```

出るのは4つ（Beads 方式のプロジェクトでは、タスク本文と `## 結果` は Beads の課題と comment から、
登録から完了までの差分は `bd history` の最初と最後の版から出る。`task-workflow` の WORKFLOW.md
「Beads 方式」）。**タスク本文と `## 結果`**（`develop/task/T-xxx.md` の `HEAD` の版。`task prune` で消したものは最後にあった版。旧形式の
時代のタスクは `develop/tasks.json` か `docs/history/tasks.md` の本文と evidence）、**登録から完了までの
タスクファイルの差分**（登録時の節といまの節、着手時に書き足した `## やること`・`## 注意`。旧タスクは
代わりに `progress.md` の小節）、**コミットと diff**、**手数**（ツール呼び出し数・エラー数・同じ
ファイルを直した回数・よく打ったコマンド）。

diff が上限で切れたら、気になるファイルだけ `git show <hash> -- <path>` で追う。
**全部は読まない**——振り返りに要るのは「本文が求めたこと」と「実際に入ったもの」の**差**で、
差の無いところを読んでも何も出ない。

**diff は大きさではなく形で見る。** 「多数のファイルに1〜3行ずつ」なら、それは判断ではなく
機械的な追随で、**人が手で書かされている**ということ。同じ行が何度出てくるかを数えると
（`git show <hash> | grep -c '^+.*<その行>'`）、次に同じ語彙を増やすときの費用がそのまま出る。

対象が5件を超えるときは、`tasks` の並びのうち**手数が多いもの・diff が大きいもの・
`dropped` のもの**から順に見て、残りは件名とdiffstatだけで済ませる。

### 3. 振り返る

材料を眺めて感想を書くのではなく、**差を探す**。次の兆候が振り返りの入口になる。

| 兆候（材料のどこに出るか） | 疑うこと | 札の候補 | 出し先の候補 |
| --- | --- | --- | --- |
| diff の大半が**同じ1行の繰り返し**（diffstat が「多数のファイルに1〜3行ずつ」の形） | 機械的な追随を人が手で書いている。語彙・定義・フィクスチャの重複 | `道具` | タスク（共通の組み立てに寄せる） |
| 同じファイルを3回以上直している（手数） | 手順の順序が悪い・前提を調べずに書き始めた | `診断違い`・`実装の誤り` | タスクの書き方（`plan-tasks`）／規約 |
| ツールのエラーが多い（手数） | 環境の前提がタスク本文に無かった | `操作の誤り`・`道具` | タスク本文の `## 注意` に書くべきこと |
| 検証コマンドを何度も打ち直している（手数） | 落ちる原因が規約に書かれていない | `揺れ`・`実装の誤り` | 規約への追記 |
| 運良く助かった（打ち直して1回で通った・単独なら通る・受け入れで偶然気づいた） | 同じ揺れが、次は本当の失敗として出る芽を見逃している | 打ち直して通った・単独なら通る → `揺れ`／受け入れで偶然気づいた → 気づいたものに合わせる | 規約への追記 |
| 本文が指した場所と diff の場所がずれている | 調査が本文に落ちていない・設計の理解が古い | `正典の不備`・`診断違い` | 正典（`docs/`）の記述が実物とずれている |
| 完了条件に無かったものが diff に入っている | タスクの切り方が粗い／必要な追随が暗黙になっている | `頼まれていない拡張`・`正典の不備` | タスクの書き方／規約 |
| `## 結果` が完了条件を覆っていない | 受け入れが甘い | `自己申告の不正確さ` | 結果の書き方（`task-workflow`） |
| 着手時の `## やること` が、登録時の `## 背景` の前提を覆している（登録から完了までの差分） | 登録が粗い・登録から着手までに前提が動いた | `正典の不備` | 登録の書き方（`plan-tasks`） |
| 複数のタスクで同じ手作業が出ている | 道具にできる | `道具` | タスク（スクリプト化） |
| `difficulty` を途中で上げた／明らかに過剰だった | 見立ての基準がずれている | `正典の不備` | `difficulty` の基準 |

札の候補は目安で、読み直して別の札が当たるならそちらを付ける（札と色は節「札と1行の書式」）。

**出すかどうかの物差しは1つだけ**: *次に同じ状況が来たときに、誰かの振る舞いが変わるか*。
変わらないなら書かない。一度きりの事故、そのタスク固有の事情、「うまくいった」の確認は、
書いても次に効かないので落とす。

**同じ話に畳めるものは1つにまとめる。** 「T-302 で〜」「T-318 でも〜」が同じ原因を指しているなら、
それは1件の findings で、タスクIDは根拠として並べる。1回の振り返りで3件を超えたら、
畳み方が足りていないと疑う。

**思いつきを足さない。** 材料に根拠が無い改善案は、振り返りではなく思いつきで、
ドラフトに混ぜると出どころが分からなくなる。

### 4. ドラフトに積む

1件を1ファイルにして `develop/draft/` に足す（既存のファイルは書き換えない）。ファイル名は
`<YYYY-MM-DD>-<英小文字・数字・ハイフンの要約>.md`（`task-workflow` の `WORKFLOW.md`「指示メモ」）で、
中身はこの形:

```markdown
# <何を変えるか（1行）>（振り返り: T-302, T-318）

- 札: <色> <札>
- 根拠: <材料のどこにどう出ていたか。数で言えるものは数で>
- 出し先: <どのファイルのどの節に足すか / タスクにするなら何をするタスクか>
```

`- 札:` の行は1つだけ（節「札と1行の書式」の語彙から1つ。色は畳んだうちの重いほう）。札が2つ要るなら
別の話なので、ファイルを分ける。行頭の `- 札:` は承認後も `docs/history/direction.md` に中身ごと
移るので、形を変えない。

`develop/direction.md` の `## ユーザーから` には書かない（あそこはユーザーの入口）。ここに積んだ
ものは、ユーザーの承認を得てから `/plan-tasks` がタスクにする（`task-workflow` の `WORKFLOW.md`「指示メモ」）。

**findings が0件でも、それは失敗ではない。** 範囲は振り返り済みとして記録し、0件だったことを
報告する。無理に絞り出すと、次からドラフトが信用されなくなる。

### 5. 記録してコミット

`develop/retrospective.md` を更新する。

- 先頭の `最後に振り返ったコミット:` の行を、**範囲の末尾（`scan.py` が出した `range` の右側）**
  に書き換える
- 「振り返りの履歴」の**先頭**に小節を1つ足す（新しい順）

```markdown
### YYYY-MM-DD `<since>`..`<head>`（<N>コミット / T-XXX, T-YYY）

- <findings の1行要約> → `develop/draft/<ファイル名>`
- 振り返ったが出さなかったもの: <あれば1行。無ければこの行ごと省く>
```

`git add` する前に整形コマンドを打つ（`タスク運用`節が `なし` なら不要）。打ったら
`develop/retrospective.md` と足したドラフトのファイルを指定してコミットする
（`git add -A` を使わない）。件名は `振り返り <since>..<head>（<N>コミット）` の形にし、タスクIDは
件名に置かない（タスクのコミットと混ざると `scan.py` の割り付けが狂う）。コミットしたら
`python3 ${CLAUDE_SKILL_DIR}/../task-workflow/scripts/task.py ship` で `main` へ送る（`SHIPPED` 以外で
止まったら、先頭語と行をそのまま報告して預ける。扱いは `next-task` スキルの手順8の表と同じ）。

**初回**は記録ファイルを作るところから。この雛形をそのまま置く:

```markdown
# 振り返りの記録

最後に振り返ったコミット: `<hash>`

<!-- 上の1行だけが機械の読む値（skills/retrospect/scripts/scan.py）。形を変えない。
     振り返りの出力そのものは develop/draft/ にドラフトのファイルとして積む。
     ここに残すのは「どこまで見たか」と「何を出したか」の索引だけ。 -->

## 振り返りの履歴
```

## 1件だけ振り返る（`/next-task` の中から）

`/next-task` が受け入れ（手順6）のあと・`task done` の前に、**メインが**この節だけを読んで行う。
`/loop` から回っているときも走る。範囲は `material.py` に渡すタスクID 1つで、
`develop/retrospective.md` は読まず書かない（並行する作業ツリーが同じ行を取り合わない）。
上の「守ること」2・3はそのまま効く。

1. **数を取る**。本文と diff は受け入れで読み終えているので、手数の数行だけを出す:

   ```bash
   python3 ${CLAUDE_SKILL_DIR}/../retrospect/scripts/material.py . T-XXX --signals
   ```

   `-`（トランスクリプトが無い。委譲せずメインで進めたときなど）なら、受け入れで自分が見たことだけで判定する
2. **兆候に当たるかを見る**。当たりの目安:

   | 兆候 | 見る場所 | 当たりの目安 | 札の候補 |
   | --- | --- | --- | --- |
   | 検証コマンドの打ち直し | `よく打ったコマンド`／受け入れで自分が打った回数 | 検証コマンドが3回以上／受け入れで落ちて打ち直した | `揺れ`・`実装の誤り` |
   | 運良く助かった | 委譲先の friction log／受け入れ（手順6）で自分が検証コマンドを打ち直して通した記録 | 打ち直したら1回で通った・単独で実行したら通った・受け入れで偶然気づいた、のどれか1回でもある | 打ち直して通った・単独なら通る → `揺れ`／受け入れで偶然気づいた → 気づいたものに合わせる |
   | 同じ所を直し直した疑い | `同じファイルを2回以上直した` | 同じパスが `×3` 以上（差し替え箇所の数ではなく、直し直した疑いがあるかで見る） | `診断違い`・`実装の誤り` |
   | ツールのエラー | `エラー` | 3件以上 | `操作の誤り`・`道具` |
   | 完了条件に無い差分 | 受け入れで読んだ `git diff` | `## 完了条件`・`## やること` のどれにも当たらない変更がある | `頼まれていない拡張` |
   | 受け入れのときにメインが直したもの | 自分の受け入れ | 1つでも直した | 直したものに合わせる（規約に反していた → `制約違反`、報告と実物が違った → `自己申告の不正確さ`） |
   | 報告に残した気になる点 | 委譲先の報告に載った friction log（`- <色> <札>: …` の行。「なし」なら何も起きていない）・受け入れで自分が気づいて直さなかったこと | `赤` の行が1件でもある（完了報告に書くだけで終えず、手順4の物差しにかける。既存のタスクが扱っているものは落とす）。`黄` だけなら他の兆候と合わせて判断する。行自体が無ければ書き忘れとして扱う | 行に付いた札。無ければ節「札と1行の書式」で付ける |
   | `task ship` の失敗（`VERIFY_FAILED` など） | ― | この時点ではまだ起きていない。止まったら `/loop` も止まって人に預かるので、ここでは扱わない | ― |

3. **当たらなければ何も積まない**（「うまくいった」は書かない）。`## 結果` に `- 振り返り: 兆候なし` を足す
4. **当たったら、その箇所だけ**材料を読み直し（`git diff -- <path>`、要れば `--signals` を外して
   `material.py` を打つ）、手順3の物差し（次に同じ状況が来たときに振る舞いが変わるか）にかける。
   変わるものだけを手順4の形（`（振り返り: T-XXX）` の見出しと `- 札:` の行）で `develop/draft/` にファイルとして積む。
   `## 結果` には `- 振り返り: <当たった兆候>（ドラフト N件）` を足す（物差しで落としたら `0件`）

記録は `## 結果` の1行だけで、行頭の `- 振り返り:` は機械が読む（`scan.py` の `reviewed`。
`task-workflow` の `WORKFLOW.md`「結果の書き方と知見の置き場」）。積んだドラフトのファイルは、
`/next-task` の手順7で作業と同じ1コミットに入る。

## 報告のフォーマット

まとめての振り返りの最後に次を1行ずつ示す（1件ごとの振り返りは `/next-task` の完了報告に1行）。

- 振り返った範囲（`<since>..<head>`）とコミット数・タスクID
- ドラフトに積んだ件数（0件ならそう言う）と、それぞれの1行要約
- 材料が欠けていたものがあれば、何が無かったか（トランスクリプトが残っていない等）
- 記録のコミットハッシュと `SHIPPED` の範囲

## 他のプロジェクトで使うとき

**前提は `task-workflow` の運用**（`develop/task/` / `develop/draft/` と `docs/history/`、
**コミットの件名にタスクIDを置く**）。この運用のプロジェクトなら、置き場も
IDの形も同じなので何も変えずに動く。

前提が揃わないプロジェクトでは、スクリプトは落ちずに `-` と欠席の理由を出す（材料が減るだけ）。
そのうえで次の4つが合わないなら、合わせるか、このスキルを使わない:

| 前提 | 使っているところ | 合わないときの影響 |
| --- | --- | --- |
| タスクIDが `T-` + 3桁以上 | `scan.py` の割り付け / `material.py` の照合 | 全コミットが `unmapped` になり、振り返る単位が消える |
| コミットの件名にタスクIDがある | 同上 | 同上 |
| `develop/task/`（旧タスクは `docs/history/`）にタスクがある | `material.py` の材料2つ | 材料が diff と手数だけになる |
| ドラフトを `develop/draft/` に1件1ファイルで置く | 手順4の出し先 | 積む先が無い。プロジェクトの「未対応の指示の置き場」に読み替える |

送り方は `task ship` が CLAUDE.md の `- ブランチ:` に従って決める（このスキルは「2ファイルを指定して
コミットし、`task ship` で送る」としか決めていない）。

## このスキルがしないこと

- **ドキュメントを直さない・タスクを登録しない。** 承認ゲートの手前で止まる（上の「守ること」2）
- **まとめての振り返りは `/loop` に載せない。** 手で呼ぶ（無人で広い範囲を見ると、根拠の薄い
  findings がドラフトに溜まり続ける）。`/loop` の中で走るのは1件ごとの振り返りだけで、兆候に
  当たったときしか積まない
- **タスクファイルを消さない。** 消すのは `task prune`（`/next-task` の手順7a）。手順5で基準点を
  進めると、読み終えた `done`・`dropped` が次の `task prune` の対象になる
- **タスクの是非を蒸し返さない。** 「あのタスクはやるべきでなかった」は振り返りの対象外で、
  見るのは*やり方*だけ
