# 様式の一覧

アプリの性質に対して候補を立てるときに引く一覧。各様式について、**効く性質**・**合わない性質**・
**要求するディレクトリの形**を書く。「合わない性質」に当てはまるのに選ぶときは、補い方を提案書に書く。

様式は排他ではない。「共有契約 + クライアント/サーバ分割」の中で、サーバ側だけ「ポートとアダプタ」を
使う、といった組み合わせはふつうにある。組み合わせるときは、どの層にどの様式を当てたかを明示する。

## 目次

1. 単一モジュール（層を切らない）
2. 層状（プレゼンテーション / ドメイン / データ）
3. ポートとアダプタ（ヘキサゴナル）
4. 共有契約 + クライアント/サーバ分割
5. 縦切り（機能ごと・フィーチャースライス）
6. パイプライン（変換の連鎖）
7. イベント駆動（発行と購読）
8. プラグイン（核と拡張点）
9. 状態機械を中心に置く
10. UI の単方向データフロー（MVU / Elm 風）

---

## 1. 単一モジュール（層を切らない）

**効く性質**: 境界が1つ以下、実行環境が1つ、ファイルが十数個まで、利用者が作者のみ。

**合わない性質**: 外部との境界が2つ以上ある（テストでそこを差し替えたくなる）。

**ディレクトリの形**: `src/` 直下に概念ごとのファイル。ディレクトリは作らない。

小さなアプリに層を切るより、まずこの形で「ファイル名が概念になっているか」だけを守る。
境界が増えた時点で 3 か 4 へ進む。

## 2. 層状（プレゼンテーション / ドメイン / データ）

**効く性質**: 要求応答型で、永続化された状態を中心に回る（典型的な Web アプリ・業務アプリ）。
ドメインのルールが厚く、入出力の形式より長生きする。

**合わない性質**: ドメインのルールが薄く、外部との境界の扱いが仕事の大半（統合・仲介型のアプリ）。
そこに層状を当てると、ドメイン層が空になり、配線だけが残る。

**ディレクトリの形**:

```
src/
  presentation/   # 入出力の形式。ドメインを呼ぶ。データ層を直接触らない
  domain/         # ルールと型。他の層に依存しない
  data/           # 永続化・外部 API。ドメインの型を使うが、ドメインから呼ばれない（依存逆転を使う場合を除く）
```

依存の向きは上から下（presentation → domain ← data の形にするなら、data がドメインの
インターフェースを実装する）。

## 3. ポートとアダプタ（ヘキサゴナル）

**効く性質**: 外部との境界が複数あり（子プロセス・ネットワーク・ファイル・ホスト環境）、
**差し替えたい**（テストで偽物にする、将来別のホストに載せる）。核のロジックが境界から独立して
テストできると価値がある。

**合わない性質**: 境界が1つで差し替えの予定もない。ポートが1つの実装しか持たないなら、
インターフェースは儀式にしかならない。

**ディレクトリの形**:

```
src/
  core/           # 核。ポート（インターフェース）を定義し、アダプタを知らない
  adapter/        # ポートの実装。外部ごとに1つ。核から呼ばれ、核を呼ばない（入口のアダプタは核を呼ぶ）
  cli.ts          # 組み立て。核とアダプタを結ぶ唯一の場所
```

「ホスト依存の操作を1つのアダプタに閉じ込める」という規約があるリポジトリは、名前を使っていなくても
この様式の一部を採用している。

## 4. 共有契約 + クライアント/サーバ分割

**効く性質**: 同一言語で **2つ以上の実行環境**（サーバとブラウザ、デーモンと CLI）があり、
両者がやり取りするメッセージの型を共有する。片方だけを差し替えたり、テストしたりしたい。

**合わない性質**: 実行環境が1つ。契約を切り出しても、使う側が1つなら層として意味を持たない。

**ディレクトリの形**:

```
src/
  protocol/       # 両側で共有する契約（型・畳み込み・検証）。他の2つに依存しない
  core/           # サーバ側。protocol に依存。ui を知らない
  ui/             # クライアント側。protocol に依存。core を知らない
```

契約の層は「両側から見える最小限」に保つ。ここが太ると、両側の変更が常に契約の変更を伴うようになる。
サーバ側の内部で境界が複数あるなら、`core` の中に 3 を組み合わせる。

## 5. 縦切り（機能ごと・フィーチャースライス）

**効く性質**: 機能同士が疎で、機能を足す・消すことが変更の中心。1つの変更が1つの機能の中で閉じる。
チームが機能単位で分かれている。

**合わない性質**: 機能横断の関心（認可、描画基盤、プロトコル）が厚く、それが変更の中心。
縦切りにすると同じものが各機能に複製される。個人開発の小さなアプリでは、機能の境界が
まだ固まっておらず、切り直しが続く。

**ディレクトリの形**:

```
src/
  feature/
    <name>/       # その機能の入口・ロジック・入出力を1箇所に
  shared/         # 機能をまたぐもの。ただし「置き場所」の名前にならないよう概念ごとに分ける
```

## 6. パイプライン（変換の連鎖）

**効く性質**: 入力を段階的に変換して出力する（ビルド、テキスト処理、ETL、レンダリング）。
各段が純粋な変換で、段の順序が固定。

**合わない性質**: 段の間に双方向のやり取りや状態の共有がある。

**ディレクトリの形**: 段ごとにディレクトリまたはファイル。段の名前は動詞ではなく **その段が出すもの**
（`parse` ではなく `ast`、のように出力の概念）で付けると依存の向きが読める。

## 7. イベント駆動（発行と購読）

**効く性質**: **外からイベントが流れ込む常駐プロセス**（SDK やソケットからの構造化イベント、
ファイル監視、UI の入力）で、イベントの種類ごとに反応を切り替える。イベントの順序が意味を持つ。

**合わない性質**: 要求と応答が1対1で対応する。イベント駆動にすると、対応関係が読めなくなる。

**ディレクトリの形**: 「受け取る（境界）→ 畳み込む（状態を更新する純粋な関数）→ 描く／送る（境界）」の
3つを分ける。畳み込みは純粋に保つ（イベント列だけからテストできる）。

```
src/
  event/          # イベントの型と検証（境界で1回だけ）
  state/          # 畳み込み。イベント → 新しい状態。副作用なし
  render/         # 状態 → 出力
```

4 と組み合わせるなら、`event` と `state` は契約の層に置き、両側で共有する。

## 8. プラグイン（核と拡張点）

**効く性質**: 核は安定していて、差し込む部品（キャラクターパック、テーマ、フォーマッタ）が増える。
部品は定義ファイルや規約で表現でき、核のコードを変えずに足せる。

**合わない性質**: 拡張点が1つで、部品も1つ。拡張の仕組みが部品より重くなる。

**ディレクトリの形**: 核の中に「拡張点の契約」を置き、部品はコードの外（`pack/`・`plugin/`・設定
ファイル）に置く。「中身をコードに書かない」という規約はこの様式のサイン。

## 9. 状態機械を中心に置く

**効く性質**: 状態の遷移が仕様の中心（セッションの開始・待機・応答中・許可待ち・終了のような
明確な状態と遷移）。不正な遷移を型やテストで落としたい。

**合わない性質**: 状態が少なく、遷移の制約も無い。

**ディレクトリの形**: 状態と遷移を1つの概念（ファイルまたはディレクトリ）にまとめ、
他はそこから読むだけにする。7 の `state` をこの形にすることが多い。

## 10. UI の単方向データフロー（MVU / Elm 風）

**効く性質**: ブラウザや TUI の描画があり、状態 → 描画 → 入力 → 状態更新の輪が閉じている。
描画を状態の関数として書きたい。

**合わない性質**: 描画が無い、または描画がホスト側（別プロセス）に完全に委譲されている。

**ディレクトリの形**: クライアント側の中で `model`（状態）・`update`（畳み込み）・`view`（部品）を
分ける。4 の `ui` の中身の形として使う。

## 候補を選ぶときの手がかり

| 性質 | まず見る様式 |
| --- | --- |
| 実行環境が2つ以上、同一言語 | 4 |
| 外部との境界が複数、差し替えたい | 3 |
| 外からイベントが流れ込む常駐プロセス | 7（4 の中に置くことも多い） |
| 中身を定義ファイルで差し込む | 8 |
| 状態遷移が仕様の中心 | 9 |
| 永続化された状態とルールが中心 | 2 |
| 機能単位で疎、足し引きが中心 | 5 |
| 入力から出力への固定の変換 | 6 |
| 境界1つ、ファイル十数個 | 1 |
