# 提案書のひな形

提案書はこの節の並びで書く。節の名前は変えてよいが、**順番と役割は保つ**（性質 → 候補 → 目標 →
差分 → 移行 → 採らなかった案 → 未決事項）。読む人は「なぜこの形か」を上から順に追えるようになる。

各節の粒度の目安を添える。長さより **根拠（ファイル名・行・コマンドの出力）** が付いているかを優先する。

---

```markdown
# アーキテクチャ提案: <アプリ名>

作成: <日付>。対象コミット: <ブランチ> の <短い SHA>。<リポジトリには書き込んでいない、など>

<結論を3行。性質の要約・選んだ様式・最初の段階。本文を読む前に採否を判断できるように>

## 1. アプリの性質

<軸ごとに1〜2行と根拠。SKILL.md 手順1の表の軸を使う。根拠が無い軸は「未確認」と書いて 7 へ>

| 軸 | 読み取ったこと | 根拠 |
| --- | --- | --- |
| 何を中心に回るか | | |
| 外の世界との境界 | | |
| 状態の持ち方 | | |
| 実行環境の数 | | |
| 変わりやすい場所 | | |
| 守られている制約 | | |
| 利用者と開発体制 | | |
| テストできる範囲 | | |

### 現状の依存の辺

<ディレクトリ同士の import を数えた表。grep のコマンドも残す>

## 2. 候補と選択

<現状の様式が性質に合っているなら、最初にそう書いて土台を固定し、候補は「土台の中の割り方」で立てる。
「現状維持 + 検査だけ足す」はたいてい候補 A になる>

### 候補 A: <様式名>
- 効く性質:
- 合わない点と補い方:
- 要求する形:
- 確度: 固い / 試す価値あり / 推測

### 候補 B: <様式名>
（同上）

### 選んだもの: <A または B、または組み合わせ>
<選んだ理由を性質に対応づけて。選ばなかった候補を捨てた理由も>

## 3. 目標のディレクトリ構造

<木。ディレクトリごとに「住むもの」と「置いてはいけないもの」を1行ずつ>

### 許す依存の辺

<A → B の一覧。既存の依存テストがあれば、その変更内容。辺が多く向きが変わるなら、現状と目標の図を並べる（任意）>

### 名前について

<新しいディレクトリ名や層の名前の出どころ。用語集に足すなら、その項目の文面案を1〜2行>

## 4. 現状との差分

<動くファイルの一覧。動かさないものも明記>

## 5. 移行の段階

<各段階: 何をするか / 終わったと分かる証拠 / 通すチェック / 確度。最初の段階は「ファイルを動かさない」が理想>

## 6. 採らなかった案

<候補以外で検討して捨てたもの。既存の設計書にある「採らなかった案」と重複するなら参照だけ>

## 7. 未決事項

<聞けなかった／決めきれなかったこと。仮定と、それが外れたときに変わる箇所。
```
