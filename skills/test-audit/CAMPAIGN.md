# テストを刈り込むキャンペーン

キャンペーンモードは、1つのサブシステムのテストの面を丸ごと1つの変更（PR）で刈り込む。対象は
1つのプラグインや機能（たとえば `extensions/telegram`）か、コアの1つの領域。[SKILL.md](SKILL.md) の
価値の基準・残す基準・候補の証拠・検証は、どのレーンにもそのまま効く。このファイルが足すのは、作業の
順序と、1回のキャンペーンをやり通して得た教訓。各段は完了の条件で終わる。**前の段が終わる前に次の段を
始めない。**

以下の例に出てくる Telegram は、原典（openclaw）で実際に行ったキャンペーンのもの。

## 1. 基準線

固定した `main` の SHA で、サブシステムのテストとテスト支援の行数、すべてのテストファイルの
通る／落ちるを記録する。基準線で落ちているものは別の一覧に分けておく。Telegram のキャンペーンでは、
その3件すべてが古くなったテストではなく、本物の配達のバグだった。

**完了の条件**: 対象範囲のすべてのテストファイルに、記録された基準線の結果がある。

## 2. レーンと棚卸し

テストの面を、ファイル名の接頭辞ではなく**本番側の持ち主の境界**に沿って**レーン**に分ける。
Telegram では、アカウント・コマンド・コンテキスト・振り分け・受信・送信・永続化・通信・共有・
ハーネス・ライブ／QA の場面だった。共有のコアの境界にあるそのサブシステムのケースと、その QA や
ライブの証明のハーネスのテストも含める。

**完了の条件**: サブシステムが持つすべてのテストファイルと QA の場面が、ちょうど1つのレーンに
属している。

## 3. レーンごとの読み取り専用の台帳

レーンごとに、読み取り専用のエージェントを1つずつ割り当てる。エージェントは割り当てられたテストを
パラメータの表まで含めて全部読む。本番側の持ち主と、その入口・呼び手・履歴・CI での実行経路も読む。
テストの宣言を1つずつ、印を1つ付けて書き出した**台帳**に入れる。`it.each` のような表駆動のテストは
1つの宣言として数える。ただし行ごとに印が違うなら、行ごとに印を付ける。

- `R`: 残す。守っている契約と、捕まえるバグを名指しする。より良い名前のファイルへ移すだけの
  残すテストは、移すことを書き添えて `R` のまま
- `F`: 契約は残し、アサーションを直す。たとえば、複数の項目のうち1つだけが欠けても通ってしまう
  空振りの否定
- `C`: まとめる。アサーションを吸収する持ち主を先に名指しする（兄弟の表のケース、より強い境界の
  テスト群、別のパッケージにある共有の持ち主）
- `D`: 消す。残る証明を名指しする。または、契約が存在しない理由を書く

**テストは名前ではなくアサーションで判定する。** Telegram のあるテストは、進捗の窓を片付けることを
名前に掲げながら、窓が片付いて**いない**ことを検査していた。

**完了の条件**: レーンのすべての宣言に、印と1行の証拠がある。

## 4. レーンごとの層の計画

テスト単位の台帳は入力であって、編集の一覧ではない。台帳から始めて、読み取り専用の2回目の読みで
冗長な**層**を探す。Telegram では、いくつかの振り分けのテスト群が、1つのモックしたプレビューを通して
同じ共有の合成器を再演していた。その周りには、本物のストリームや HTTP のフィクスチャを使うより強い
テスト群があった。契約ごとに、**残す側（keeper）**のテスト群を名指しする。モックした協力者より、
偽のネットワークを当てた本物の通信の境界を選ぶ。この読みで見つけた台帳の誤りは直す。

**完了の条件**: レーンごとの計画が、退役させるファイル・契約ごとの残す側・残す側へ運ぶアサーション・
消せるようになるテスト専用の本番コードの継ぎ目を名指ししている。

## 5. 切り替え

レーンごとに編集する。共有のハーネスや支援ファイルへの変更は、1人の持ち主を通して順番に行う。
各レーンと一緒に、そのレーンで消せるようになったテスト専用の本番コードの継ぎ目（注入の引数・getter・
リセット用の export・間接の層）を消す。移したテスト群は、CI での実行経路やテストの一覧があれば
そこに登録する。縮む一方の行数の上限の基準線があれば更新する。テストの持ち主についての長く効く
ルールは、このキャンペーンで実際に見つけた誤りから引き出して、サブシステムの `CLAUDE.md`
（プロジェクトが `AGENTS.md` を使っているならそちら）に書く。

**完了の条件**: すべてのレーンの計画が適用され、各レーンの残す側が通る。

## 6. 保全のレビュー

完了を言う前に、独立したレビュアーに、消した覆いと残す側を突き合わせてもらう。レビュアーは境界の
グループごとに1人。見るのは、唯一の証明を失った契約。できたばかりの、落ちようのないアサーション
（本番のコードが決して届かない拒否の行など）も見る。Telegram のレビューでは、本物の穴が9つと、
届かないアサーションが1つ見つかった。

戻した契約ごとに、本番側の持ち主に**わざと1つの変異**を入れ、残す側が赤くなることを確かめる。
そのあと、ソースをバイト単位で元に戻す。

**完了の条件**: 報告されたすべての穴が、戻されたか、ソースの証拠つきで退けられている。戻した
すべての契約に、捕まった変異がある。

## 7. プロダクトの欠陥

基準線での失敗が残す側まで生き延びたら、それはバグ報告である。持ち主のところで別のコミットとして
直し、本物の利用者の流れで証明する。修正を戻して古い振る舞いが出ることを見せる**対照**の実行も行う。
見つけた無関係なプロダクトの食い違いは、キャンペーンの中で直さず、後続の作業として記録する。

**完了の条件**: 直した欠陥ごとに、同じハーネスでの、落ちる対照と通る候補がある。

## 8. 突き合わせと引き継ぎ

キャンペーンは `main` の多くのコミットより長く続く。コミットの多い長いキャンペーンは、rebase ではなく
`main` を merge する（プロジェクトの Git 運用が別の決まりを持つなら、そちらに従う）。キャンペーンで
消したファイルを `main` が変えていたら、消したほうを保つ。代わりに新しい契約を残す側へ移し、`main` が
足した新しい退行テストがすべて居場所を持っていることを確かめる。取り込んだ先頭で、サブシステムの
テスト全体を走らせ直し、ライブの証明をやり直す。

これだけ大きな差分では、レビューの道具にはファイルの一覧が途中で切れて見えることを想定しておく。
汎用の互換フラグについての保守者の判断は、関門のほうを書き換えずに、PR の証拠に記録する。

[SKILL.md](SKILL.md) の報告に加えて、次を添えて引き継ぐ:

- 基準線と最終のテスト／テスト支援の行数（本番コードは分けて数える）
- レーン、退役させた層、残す側
- 見つかった保全の穴と、その変異
- 対照と候補の証明つきの、プロダクトの欠陥
