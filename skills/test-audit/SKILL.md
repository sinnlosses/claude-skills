# テスト監査

3つのモードと、1本の価値の基準。**作成モード**は、新しく書く・変えるテストをすべて書いた時点で関門に
通す。**監査モード**は、ソースをなぞり直しているだけのテスト・より強い証明と重複しているテスト・振る舞いを
実装に結合させているテスト・テスト専用の本番コードの継ぎ目を生かし続けているテストを、範囲を絞って
一掃する。広い範囲の監査は、まとまりのある後続の変更に分けて続ける。**最適化するのは確信の強さで、
消した件数ではない。** **キャンペーンモード**は、1つのサブシステムのテストの面（ある機能やコアの領域が
持つテストファイルすべて）を丸ごと刈り込む。始める前に [CAMPAIGN.md](CAMPAIGN.md) を読む。

テストファーストで振る舞いを1つずつ足していく手順は `tdd` スキルが持つ。このスキルは、そこで書く
テストが足す価値を持つかの関門と、すでにあるテストの棚卸しを受け持つ。

## 作成の関門

テストを足す前に、4つの問いに答える。答えられない問いが1つでもあれば、まだ足さない。

1. どの観察できる振る舞い・不変条件・独立した契約を守るのか
2. どんなもっともらしい退行があれば、このテストは落ちるのか
3. なぜ既存のテストではその失敗を捕まえられないのか。契約ごとに、**最も強い境界に主たるテストの
   持ち主を1つ**置く。別の層でも書くなら、その層に固有のリスク（持ち主からは届かない通信や
   ライフサイクルの失敗など）が要る。ほとんど同じテストを増やすより、表駆動のケースや共有の
   フィクスチャを伸ばすほうを選ぶ。重複した準備のコードは同じ変更の中でまとめる
4. 本番の呼び手が誰も要らない、本番コードの継ぎ目（export・フラグ・ラッパー・注入のフック）を
   要求していないか。要求しているなら、テストのほうを本物の境界へ移す

そのうえで、テストを[ゴミの型](#ゴミの型)のすべてと突き合わせる。1つでも当たれば関門を通さない。
ただし[残す基準](#残す基準)が、そのテストが独立して守っている契約を名指しできるなら通してよい。
**振る舞いを保つリファクタリングで壊れるテストは、振る舞いではなく実装を検査している。** 入れる前に、
持ち主の境界で書き直す。

バグの退行テストは、**直す前のコードで意図した理由により落ち、持ち主の境界で直したあとに通る**
ものでなければならない。落ちるところを見せたことのない退行テストが証明しているのはモックであって、
修正ではない。1つのバグは持ち主の境界での退行テスト1本で覆う。バグが通り抜ける層ごとに同じ場面を
再演しない。

## ゴミの型

2つのモードで共有するチェックリスト。作成の関門はどれかに当たる新しいテストを拒み、監査はどれかに
当たる既存のテストを探す。

- アサーションの無い、カバレッジを稼ぐだけの探り
- 自分自身との比較や、同じものを写すだけの恒等なコピー
- フィクスチャ・一覧・マニフェスト・export の一覧を写しただけのもの
- ソース・import・文字列をそのまま grep するもの
- 本物の境界で重複して検査されている、非公開の述語や呼び出しの形のテスト
- 同じ契約を何度も呼んでいるだけのもの
- 共有のヘルパーを、提供者ごとの場所で再演しているもの
- テスト専用の export・グローバル・ラッパーを保つことだけが目的のテスト
- 呼び手がテストしかいない、死んだ本番コード
- 期待値を、検査対象のヘルパーやレンダラ自身に作らせているもの
- 検査している振る舞いそのものをモックが実装しているもの、または1つの同じモックが別々の API の
  代わりをしているもの
- 本来は持ち主が生むはずの受領・受け入れ・コールバックの順序をフィクスチャが与えているもの、
  または経路が一度も書かないストアに対して永続化を検査しているもの
- フラグが約束する配達や応答を実際に動かさず、宣言されたフラグを言い直しているだけの能力テスト
- 無関係な理由で通ってしまう否定の対照（別のガードによる拒否や、本番の経路が決して届かない拒否など）
- 名前やフィクスチャが、入力が実際に動かす以上のことを約束しているもの（「窓を片付ける」という
  名前のテストが、窓が片付いて**いない**ことを検査している、など）

## 価値の基準

テストは、振る舞い・もっともらしい退行・独立して意味のある契約を守ることで、保守の手間に見合う。
監査では、振る舞いを保ったソースの組み替えで変更を強いられる既存のテストは**疑わしい**が、
自動的に消してよいわけではない（新しく書くものは作成の関門がそのまま拒む）。

候補を判定する前に、テストの全体と、本番側の持ち主・その入口・呼び手・呼び先・兄弟の実装・重なる
テスト・CI での実行経路・関係する履歴を読む。最初にルートと対象範囲の `CLAUDE.md`（あれば
`AGENTS.md` も）を読む。依存先に支えられた振る舞いだとテストが主張しているなら、依存先のソースや
型を直接確かめる。

## 洗い出し

洗い出しは読み取り専用に保ち、編集する前に証拠を報告する。範囲が広いときは、使えるなら並列の
洗い出しの**レーン**を走らせる。レーンはプロジェクトの構造に合わせて切る。たとえば:

- コアと共有パッケージ
- プラグイン・拡張・機能ごとの領域
- UI・アプリ・スクリプト・ツール類
- 横断的な型の一掃（[ゴミの型](#ゴミの型)を全体に当てる）

キャンペーンモードの外では、推測まじりの大きな一覧より、確信の高い少数の候補を選ぶ。探すのは
[ゴミの型](#ゴミの型)。

## 残す基準

公開 API・プラグインの SDK・プロトコル・設定・マイグレーション・ストレージ・セキュリティ・
プラットフォーム・既定値・プロンプトのバイト列・言語をまたいで生成されるもの・パッケージ・リリース・
アーキテクチャの契約を独立して守っているテストは残す。ほかにも次を残す:

- 順序が観察できる振る舞いであるときの、呼び出しの順序
- もっともらしい壊れ方を持つ退行テスト
- それが最も安い独立したガードであるときの、ソースの検査。契約（利用者から見えるキー・バイト列・
  パス）が変わったときに落ち、識別子だけのリファクタリングでは生き残るもの
- 基準線で落ちる残すべきテスト。プロダクトのバグかもしれないものとして扱い、再現させて、消すのでは
  なく持ち主を直す

**静的であること・遅いことは、消す理由にならない。** 実装に似て見えるテストが、それでも独立した契約で
あることはある。消す前に、そうでないことを証明する。

## 候補の証拠

編集する前に、下の欄をすべて記録する。欠けた欄が1つでもあれば、その候補はまだ消せない。

- テストの正確な名前と場所
- 実際に検出できる失敗は何か
- 覆われている本番コードやテスト支援の継ぎ目の、テスト以外の呼び手
- 残る、持ち主の境界でのより強い証明。または、証明が要らない理由
- 関係する履歴と、テストや継ぎ目が存在する理由
- 消せるようになる本番コードやテスト支援のコード
- リスクと、絞った検証のコマンド

## 編集の形

持ち主の境界でまとまる1つのバッチを選ぶ。役目を終えたテスト専用の export・グローバル・ラッパー・
死んだ本番の経路は、別名で残さずに消す。残す退行テストは、本来の持ち主のところへ移す。パッケージや
依存について繰り返されているアサーションは、1つの汎用の契約にまとめる。

本番コードの行数が純減する変更を選ぶ。同じ実装を言い直すだけの代わりのテストは足さない。消した件数を
増やすために、確信の持てない候補を片付けに回さない。

## 検証

テストランナー（とくに watch モード）がその作業ツリーで走っている間は、ソースもテストも編集しない。
コマンドはプロジェクトの `CLAUDE.md` に書かれたもの（「## タスク運用」節の検証コマンド・整形コマンド
など）に従う。

1. 持ち主と兄弟の、いちばん小さな範囲のテストだけを走らせる
2. ソースの grep や計画のアサーションを消したときは、本物の契約を持っているスクリプトやドライランを
   実際に走らせる
3. 対象を絞って整形し、`git diff --check` を通す
4. リポジトリの方針が求める変更範囲の検証（プロジェクトの検証コマンド）を走らせる
5. `git diff --numstat` を見て、本番コード・ツール類と、テスト・テスト支援を分けて報告する
6. 監査の編集を終えたら、`code-review` スキルでレビューする

## 取り込みと継続

コミット・push・PR の作成・取り込みは、許されたときだけ行う。流れはプロジェクトの `CLAUDE.md` の
Git 運用に従う。まとまりのある変更を1つずつ取り込む。取り込んだら最新の `main` を取り込み直し、
次の確信の高いバッチのために読み取り専用の洗い出しをやり直す。

## 引き継ぎ

次を報告する:

- 根本原因と、消した価値の低いテストの種類
- 本番側の持ち主の簡素化
- 残した誤検知と、それがまだ価値を持つ理由
- 実際に走らせた、絞った証明と全体の証明
- 本番コードとテストの行数
- PR や取り込みの状態
- 名前を付けた後続の作業
