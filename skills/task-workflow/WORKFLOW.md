# タスク運用（tasks.json / progress.md / direction.md）の正典

`/next-task`・`/plan-tasks`・`/list-tasks` の3スキルが従うルール。3スキルは手順だけを持ち、
フィールドの定義・判断基準・アーカイブの運用はすべてここに置く（各スキルには繰り返さない）。
プロジェクト固有の値（検証コマンド・整形コマンド）は、プロジェクト側の `CLAUDE.md` の
「## タスク運用」節に書く（下記）。

## 目次

| 節                                       | 中身                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------- |
| ## ファイル配置と CLAUDE.md               | どのファイルを固定の場所に置くか、プロジェクト固有の値をどこに書くか                  |
| ## tasks.json のフィールド               | `id`/`summary`/`task`/`status`/`difficulty`/`loopable`/`passes`/`evidence`/`dependencies` の定義 |
| ## summary（一行要約）                   | 一行に収める理由と、アーカイブの `**タスク**:` 行との関係                             |
| ## difficulty（タスクの難易度）          | `haiku`/`sonnet`/`opus`の基準表と運用ルール                                           |
| ## difficulty に応じたモデルの切り替え方 | `difficulty`をサブエージェントのモデル指定にする理由と、委譲しないケース              |
| ### なぜ一致していても委譲するのか       | メインと同じモデルでも委譲する理由（文脈の隔離）と、例外を作らない根拠                |
| ## loopable（`/loop` に載せてよいか）    | `Y`/`N`の基準と、フィールドが無い旧タスクの扱い                                       |
| ## progress.md の構成                    | 「完了したこと」など3セクションの書き方と、「次にやること」を持たない理由             |
| ## 良いevidenceの書き方                  | 検証可能な形で残す例と、書かないこと                                                  |
| ## コミットメッセージ                    | タスクIDの付け方                                                                      |
| ## 指示メモ（`develop/direction.md`）    | 未タスク化の指示の置き場と、タスク化するときの判定・進め方                            |
| ## 肥大化したときのアーカイブ            | `tasks.json`/`progress.md`を増やし続けない運用。下の3小節を含む                       |
| ### いつ移すか（トリガー）               | 判定する2つのタイミングと、`tasks.json`/`progress.md`それぞれの基準                   |
| ### 何を移すか                           | `done`タスク全件・`progress.md`の過去セッション分の移し方                             |
| ### `dependencies` の扱い                | アーカイブ済みタスクIDの扱いと、依存解決のルール                                      |

## ファイル配置と CLAUDE.md

状態を持つファイルの置き場は**規約で固定**する（設定で変えられない）。スキルはプロジェクトの
ルートで動く前提で、すべて相対パスで参照する。

| ファイル                       | 役割                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| `develop/tasks.json`           | タスクの配列（正典）                                       |
| `develop/progress.md`          | 直近の進捗（3セクション。下記）                            |
| `develop/direction.md`         | まだタスクになっていないユーザーの指示                     |
| `docs/history/tasks-archive.md`    | `done` タスクのアーカイブ                                  |
| `docs/history/progress-archive.md` | 過去セッションの「完了したこと」                           |
| `docs/history/direction.md`        | タスク化が済んだ指示メモ（当時の記述のまま）               |

`develop/` の3ファイルを新しいプロジェクトに用意するのは `/setup-tasks`。骨組みは決まって
いるので手で書かない（節名がズレるとアーカイブが節を見つけられない）。

**プロジェクトごとに変わる値は2つだけで、置き場は `CLAUDE.md` の「## タスク運用」節**:

```markdown
## タスク運用

- 検証コマンド: `pnpm check`（変更後は必ずこれを通す。受け入れ判定に使う）
- 整形コマンド: `pnpm format`
- ブランチ: 作業ブランチを切る

`develop/tasks.json`・`develop/progress.md`・`develop/direction.md` で管理する。
指示は `develop/direction.md` に溜め、`/plan-tasks` でタスク化して `/next-task` で進める。
```

- **行の頭（`- 検証コマンド:` / `- 整形コマンド:`）は変えない。** スキルがこの節を
  `sed -n '/^## タスク運用/,/^## /p'` で読む
- 走らせるコマンドが無いプロジェクトは `なし` と書く。**行を消さない**（「検討して不要と
  決めた」と「まだ検討していない」を、次のセッションが区別できなくなる）
- 検証コマンドが無い場合、受け入れ判定はタスク本文の「## 完了条件」だけで行い、その旨を
  報告に書く

**設定ファイル（`develop/workflow.json`）は持たない。** 以前は置き場も予算も設定できたが、
実測した3プロジェクトとも書かれていたのは検証コマンドと整形コマンドの2つだけで、しかも
**同じ内容がそのプロジェクトの `CLAUDE.md` にも書かれていた**（片方は「各スキルが言う
チェックコマンドは `bun run check` のこと」という橋渡しの一文まで持っていた）。正典が二重に
あると片方だけ直したときに気づけない——`progress.md` に「次にやること」を置かない理由と同じ
形なので、人が読む側（`CLAUDE.md`）に一本化した。残りの値は**固定**:

| 値                        | 固定値           |
| ------------------------- | ---------------- |
| タスクIDの接頭辞          | `T-` + 3桁の連番 |
| アーカイブの置き場        | `docs/history/`  |
| `done` のアーカイブ基準   | 10件以上、または 30720B 超 |
| `progress.md` に残す上限  | 5小節、または 8192B |

ブランチ運用（作業ブランチを切るか、デフォルトブランチに直接コミットするか）は
プロジェクトの `CLAUDE.md` に従う。ここでは決めない。push はどのプロジェクトでも
スキルからは行わない（外部への反映は明示的に頼まれたときだけ）。

## tasks.json のフィールド

各タスクは以下のフィールドを持つオブジェクト。並びは `id` → `difficulty` → `loopable`
→ `dependencies` → `summary` → `task` → `status` → `passes` → `evidence`。

| フィールド     | 内容                                                           |
| -------------- | -------------------------------------------------------------- |
| `id`           | `T-` に3桁の連番を付けた通し番号（例: `T-042`）      |
| `summary`      | 何をするかの一行要約（下記）                                   |
| `task`         | タスクの内容（背景・理由が分かるように具体的に書く）           |
| `status`       | `todo` / `doing` / `done`                                      |
| `difficulty`   | `haiku` / `sonnet` / `opus`（実行に使うモデルの目安。下記）    |
| `loopable`     | `"Y"` / `"N"`（`/loop` の自動進行に載せてよいか。下記）        |
| `passes`       | 完了条件を満たしたか（`boolean`）                              |
| `evidence`     | 完了の証拠（コミットハッシュ、テスト件数、生成物へのパスなど） |
| `dependencies` | 先に完了している必要がある他タスクの `id` 配列                 |

「着手しない判断」で閉じたタスクは `status: "done"` かつ `passes: false` にし、理由を
`evidence` に書く。成功した `done` と区別できるようにするための形。

## summary（一行要約）

`task` 本文を読まずに一覧を見るための一行。**登録時に必ず埋める**（後から付けない）。

- **1行に収める。** 折り返しが必要な長さになったら、それはタスクが大きすぎる合図。
  「1コミットで説明が付く大きさ」に収まっているかを、ここで書けるかどうかで検査する
- **`task` 本文の言い換えではなく、「何をするか」を書く。** 背景・理由は `task` の担当。
  `summary` に理由を足すと一覧が読めなくなる
- 対象を識別子で書く（`ConfigDirPath` を `ConfigRootPath` に改名、など）。
  「命名を直す」のような、どのタスクにも当てはまる書き方にしない
- **`docs/history/tasks-archive.md` の `**タスク**:` 行に入る値がこれ。** アーカイブの
  エントリは `## <id>` → `**タスク**: <summary>` → `task` 本文の順で書く

## difficulty（タスクの難易度）

タスクごとに必要な判断の重さを3段階で表す。**モデル名だが「どのモデルを使うか」ではなく
「どれだけの判断を要するか」を表すラベル**として扱い、タスクを登録した時点で付ける。
難易度に応じて実行モデルを切り替える運用で、**`difficulty` の値がそのまま委譲先サブ
エージェントのモデル指定になる**（下の「difficulty に応じたモデルの切り替え方」）。ラベルの
定義そのものは「判断の重さ」のままで、モデル指定を兼ねることで変わらない。

| 値       | 基準                                                                                                                                             | 例                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| `haiku`  | 機械的な作業。判断がほぼ不要で正解が1つに定まる（ファイルの移動、名前の一括置換、ドキュメントへの追記）                                          | 型定義を1ファイルに抜き出す                              |
| `sonnet` | 通常の実装。設計判断はあるが局所的で、既存の方針・前例に沿えば決まる。複数ファイルにまたがる分割やテスト追加を含む                               | 責務ごとのファイル分割、共通テストフィクスチャの抽出     |
| `opus`   | 方針・設計そのものの判断が必要。既存の原則との衝突を解く、選択肢のトレードオフを比較する、並行性やエラー方針など間違えても気づきにくいものを扱う | 設定ファイルの運用方針決め、並列化の設計                 |

運用ルール:

- 迷ったら1段上を選ぶ（判断を要するタスクを機械的に処理させるほうが、その逆より事故が大きい）
- 「作業量が多い」ことは難易度を上げる理由にならない。**判断の質**だけで決める
- 着手してみて想定より判断が必要だと分かったら、`difficulty` を上げてから再開する
- 完了済み（`done`）のタスクには遡って付けない。実行前の見積もりに使う値なので、
  完了後は `evidence` が実績を語る

## difficulty に応じたモデルの切り替え方

**タスクを実行するときは、`difficulty` に沿ったモデルを指定したサブエージェントに依頼する。**
`haiku` のタスクは `haiku` の、`sonnet` は `sonnet` の、`opus` は `opus` のサブエージェント。
**メインセッションがどのモデルで動いているかは判断材料にしない。** ユーザーは `/model` で
メインのモデルを普通に切り替えるので、メインを基準にすると `difficulty` が実行モデルを
表さなくなる。

セッションを実行しているモデル（Claude Code のメインループ）は**自分自身のモデルを途中で
変えられない**。切り替えの手段がサブエージェントへの委譲しかないのはこのため。

- **メインのモデルと `difficulty` がたまたま一致するタスクでも委譲する。** 一致している
  なら実行モデルは揃うので、ここで委譲する理由は**モデルではなく文脈の隔離**のほう
  （下の「なぜ一致していても委譲するのか」）
- **委譲しないケース**: ユーザーへの確認が必要なタスク（サブエージェントはユーザーに
  質問できない）と、会話中の文脈に依存するタスク。これは**モデル選択とは別の軸**で、
  「どのモデルで実行するか」ではなく「サブエージェントに投げられるか」を決める。方針決めは
  メインで済ませてから、決まった作業だけを委譲する。`opus` のタスクは方針決めそのものを
  含むことが多く、これに当たりやすい。該当する場合は `/loop` の自動進行に載せず、
  ユーザーがいるセッションで扱う（**この軸を登録時に明示するのが `loopable` フィールド**。
  下の「loopable」節）。**このときだけメインセッションが実行し、実行モデルは
  `difficulty` と一致しない**
- サブエージェントは**まっさらな文脈で起動する**ため、`tasks.json` の `task` 本文だけで
  作業が完結するように書く（対象ファイル・完了条件・**検証コマンド**を通すことを明記する）
- **`task` 本文を prompt に貼り付けない。** タスクIDと、本文を読むコマンドを渡す:

  ```
  タスク本文は develop/tasks.json の id: "T-XXX" の task フィールドにある。次で読める:
  python3 -c "import json,sys; print([t for t in json.load(open('develop/tasks.json')) if t['id']==sys.argv[1]][0]['task'])" T-XXX
  ```

  貼り付けると本文がまるごと**メインの出力トークン**になる。サブエージェントが自分で読めば
  向こうの入力トークンで済み、しかも同じ内容が二重に存在しない。実測では269件中244件が
  貼り付けていて、読ませている24件より prompt が中央値で1,006文字長かった
- 委譲したタスクも、完了報告をそのまま信用せず **検証コマンド**の結果で受け入れを判定し、
  `evidence` はメイン側で書く

### なぜ一致していても委譲するのか

**メインのモデルが `difficulty` と同じでも委譲する。** 一致しているなら「実行モデルを
`difficulty` に合わせる」は委譲しなくても成り立つので、**それはここでの理由にならない**。
委譲する理由は**メインの文脈を汚さないこと**で、こちらは一致・不一致に関係なく効く。

実測（このリポジトリのスキルを使っている3プロジェクトの委譲269件）:

| 委譲がメインに残すもの | 中央値 |
| ---------------------- | ------ |
| 渡す prompt            | 約3,000文字（`opus` は3,432、`haiku` は1,833） |
| 起動時のスタブ         | 1,122文字 |
| 返ってくる完了報告     | 2,938文字（75%点 5,066、最大 13,671） |
| **合計**               | **約7,000文字** |

同じ作業をメインで実行すると、代わりに `CLAUDE.md`（あるプロジェクトで7,681文字）・
コーディング規約・対象ソース・テスト出力が**すべてメインの文脈に入る**。**`/loop` は
1セッションで何サイクルも回す**ので、この差はサイクルごとに積み上がる。

**だから例外は作らない。** 委譲しないのは下の「委譲しないケース」＝ `loopable: "N"` に
当たるときだけで、それは「文脈を節約したいか」ではなく「サブエージェントに投げられるか」
という別の軸の話。

`difficulty` が `haiku` で対象ファイルが `task` 本文に列挙されているものは、探索が要らない
ぶん往復代が相対的に高くつく。それでも例外にしないのは、**実績で `haiku` の委譲が269件中
13件（5%）しかなく**、効く場面が狭い割に「これは例外か」という判断がサイクルごとに1つ
増えるため。判断を増やさないほうを採る。

## loopable（`/loop` に載せてよいか）

そのタスクを**ユーザーのいないところで進めてよいか**を `"Y"` / `"N"` で表す。上の
「委譲しないケース」で述べた「サブエージェントに投げられるか」の軸を、判断の結果だけ
フィールドに固定したもの。`difficulty` とは**独立**で、`opus` でも `Y` はありうるし、
`haiku` でも `N` はありうる（例: 1行の設定変更だが外部サービスに反映される）。

`"N"` にするのは次のどれかに当たるとき:

- **ユーザーへの確認が必要**: 元に戻せない操作、外部への反映（push・デプロイ・課金）、
  複数案のどれを採るかをユーザーが決めるもの
- **会話中の文脈に依存する**: `task` 本文だけでは何を作るか決まらず、直前のやりとりを
  前提にしているもの
- **対話的な検証が必要**: 実機での目視確認や、検証コマンドで判定できない受け入れ

上のどれにも当たらなければ `"Y"`。**迷ったら `"N"` を選ぶ**（自動進行で事故るコストは、
ユーザーを待たせるコストより大きい）。

運用ルール:

- **登録時に必ず埋める**（`summary`・`difficulty`・`dependencies` と同じ扱い）
- 着手してみてユーザーの判断が要ると分かったら、`"N"` に直してからユーザーに預ける
- **`/next-task` を `/loop` から回しているときは `"N"` のタスクを選ばない。** 残りが
  `"N"` だけになったら「ユーザーの判断待ちのタスクのみ」として止まる。`/next-task` を
  ユーザーが直接呼んだときは `"N"` も選んでよい
- **フィールドが無い旧タスクは `"Y"` として扱う**（この運用より前に登録されたもの。
  従来の挙動と同じ）。値を遡って付け直す必要はない

## progress.md の構成

以下の3セクションで構成する:

- **完了したこと**: 何を、なぜ、どう検証したか（コミットハッシュ・テスト件数を添える）。
  1タスク＝1小節で、**`### YYYY-MM-DD 何をしたか（T-xxx）` の形**
- **未解決**: 判断が必要で保留中の事項
- **注意**: 誤解しやすい前提・外部リソースの状態など、次回セッションで踏み外しやすい点

「完了したこと」には、**新しい小節を上に積む**（節の先頭に差し込む）。アーカイブは
並びが「新しい順」であることに依存していて、逆順のファイルにかけると**新しいほうを捨てる**。
スクリプトは日付が増加する並びを見つけたら、移さずに `ERROR` で止まる。

この節は**直近ぶんだけを残し、溢れたぶんをアーカイブへ移す**（下記）。残す量は件数と
サイズの予算で決め、**「このセッション分」では切らない。** セッションはファイルから
機械的に決められないためで、新しいセッションは上の小節を誰が書いたか判別できないし、
`/loop` の1セッションは何小節も書く。日付をセッションの代用にすると、同じ日に何度も
回したときに全部が「最新」になって永遠に移らない（実際にそうなったリポジトリがある）。

**「次にやること」の節は置かない。** 未着手タスクの正典は `develop/tasks.json` で、
一覧が見たいときは `/list-tasks` がその時点の `tasks.json` から出す。`progress.md` に
写しを持つと、`develop/direction.md` を残さない理由（下の「指示メモ」）と同じことが起きる
——正典が二重になり、片方だけ直したときに気づけない。実際、この節を持っていた
リポジトリでは**全項目が完了済みなのに1万文字が残り**、別のリポジトリでは件数の内訳が
`tasks.json` とズレていた。どちらも毎セッション読まれていた。

タスクを登録した経緯・グルーピングの理由・ユーザーが決めた方針は、**タスク本文の
`## 背景`** と `docs/history/direction.md` が持つ。判断待ちの事項は「未解決」、
踏み外しやすい前提は「注意」。`progress.md` に置き場が無いものは無い。

## 良いevidenceの書き方

「完了しました」という宣言だけでは合格にしない。次のような、後から検証可能な形で残す:

- コミットハッシュ（`commit e59c410` のように）
- 検証コマンドの通過件数（テスト件数が変わっていれば増減が分かる）
- 生成物や検証ログへの具体的な参照

**書かないこと**: 設計変更の物語、検討して撤回した案、実機検証の手順の詳細、
変更したファイルの列挙。これらは後から誰も参照しないわりに `tasks.json` を肥大化させ、
毎セッション冒頭に全件読む運用のコストを押し上げる。判断の経緯を残したい場合は、
プロジェクトの設計ドキュメントか下記のアーカイブへ書く。目安として1タスクのevidenceは
**3行以内**に収める。

## コミットメッセージ

タスクに対応するコミットは、**件名の先頭にタスクIDを置く**（`T-110: コミットメッセージに
タスクIDを振る`）。`git log --oneline` にIDが出るので、後から `git log --grep='T-110'` で
そのタスクの変更だけを引ける。

- **1タスク＝1コミット**なので、IDは1件だけ書く。複数タスクにまたがる変更はコミットを分ける。
  分けられない場合に限り `T-105, T-108: 〜` とカンマ区切りで並べる
- **タスクIDを持たない作業にはIDを付けない**（運用の変更、typo修正、アーカイブなど）。
  無理に採番しない
- **過去のコミットは遡って書き換えない**。履歴の書き換えは破壊的操作で、得られるものより
  失うもののほうが大きい

IDはアーカイブ後も `docs/history/tasks-archive.md` に `## <id>` の節として残るため、
参照先が消えた識別子にはならない。

## 指示メモ（`develop/direction.md`）

ユーザーからの指示は、チャットではなく `develop/direction.md` に書く。書式は課さない
（雑な箇条書きでよい）。**このファイルは「まだタスクになっていない指示」の置き場**で、
セッション開始時に中身があれば、他の作業より先にタスク化する（`/plan-tasks`）。

- 判定は「見出し行以外に中身があるか」。`grep -v '^#' develop/direction.md | grep -v '^\s*$'`
  が空なら未対応の指示は無い
- 1項目＝1タスクとは限らない。分割も統合もしてよい。ただし**「各項目 → 生成したタスクID」の
  対応表を必ず報告する**（取りこぼしの検知点がここしかないため）
- **タスク化した時点で `develop/direction.md` を空にし、内容は `docs/history/direction.md` へ
  日付見出し付きで移す。** タスクが全部 `done` になるまで残す運用にはしない。残すと正典が
  `develop/tasks.json` と二重になり、片方だけ直したときに気づけないため。進捗の追跡は
  `develop/tasks.json` の `status` が担う
- 移すときは**当時の記述をそのまま**にし、後から書き換えない（アーカイブ全般と同じ扱い）。
  ユーザーの生の言い回しは、噛み砕いた後のタスク本文とは別の情報として残す価値がある
- 指示の前提が古い・既に対応済みだった場合は、勝手に消さずタスク化の報告に理由を書く

## 肥大化したときのアーカイブ

`develop/tasks.json` と `develop/progress.md` は毎セッション冒頭に読むファイルなので、増え続けさせない:

- `develop/tasks.json` の完了タスクの詳細な記録 → `docs/history/tasks-archive.md`
  （evidenceは「コミットハッシュ・テスト件数・アーカイブへの参照」に置き換える）
- `develop/progress.md` の過去セッションの「完了したこと」 → `docs/history/progress-archive.md`

アーカイブは当時の記述をそのまま移すだけにし、後から書き換えない（当時のファイル名・型名が
現在と違っていても履歴としてそのまま残す）。

### いつ移すか（トリガー）

判定する時点は2つある。**どちらも `develop/tasks.json` を読む／書く直後**で、増えたまま次の
セッションへ持ち越さないためにある。

- **セッション開始時**（`/next-task` の手順1）
- **タスクを登録した直後**（`/plan-tasks` の手順5）。登録がファイルを大きくした当事者なので、
  その場で判定する

**2つのファイルを同じ検査点でまとめて判定する。** 片方だけ該当したら、その片方だけを移す。

`develop/tasks.json` の基準（規約で固定。上の「ファイル配置と CLAUDE.md」）:

- `status: done` が **`archive.doneCount` 件以上**（既定 10）
- または `done` のタスクが占めるサイズが **`archive.doneBytes` 超**（既定 30KB。`json.dumps` した文字数で測る）

**`todo` のタスクはこの判定の対象外**（サイズにも件数にも数えない）。`todo` はこれから
やる作業の待ち行列で、アーカイブする先が無い。ファイル全体のサイズで判定すると、
`todo` だけで基準を超えたとき「基準は超えているのに移せるものが1件も無い」状態になり、
毎回トリガーだけが鳴って何も起きない。判定するのは**減らせるものだけ**にする。

`develop/progress.md` の基準（「完了したこと」配下の小節を、新しい順に数える）:

- 小節が **`archive.progressCount` 件を超える**（既定 5）
- または「完了したこと」節が **`archive.progressBytes` を超える**（既定 8KB）

`todo` と同じ理屈で、「未解決」「注意」の2節はサイズ判定に含めない
（アーカイブする先が無いため）。

**2つの判定とも同梱の `scripts/status.py` が行う**（`/list-tasks` が使うものと同じ）。
末尾の `archive` 行が `tasks.json` の、`progress` 行が `progress.md` の判定で、
どちらも `YES` なら該当:

```bash
python3 <task-workflowスキルのディレクトリ>/scripts/status.py develop/tasks.json
```

```
archive   NO    (done 7/10件, 24030/30720B)
progress  YES   (8小節/5件, 3969/8192B, 移す3小節)
```

`progress` 行が `ERROR` なら、小節が新しい順に並んでいない（上の「progress.md の構成」）。
並びを直すまでアーカイブしない。判定と実際の転記は同じ計算を共有していて
（`scripts/taskfiles.py`）、`status.py` が `YES` と言ったものは `archive.py` が必ず移す。

**`tasks.json` の `done` を移すときは `progress.md` も同じ検査点で見る。** 片方だけ
メンテされて片方が伸び続けるのを防ぐため、判定を別々のタイミングに置かない。

### 何を移すか

- `done` のタスクは**全件**アーカイブする（直近セッションで完了した分も含む）。直近セッションの
  記録は `develop/progress.md` の「完了したこと」が担うため、`develop/tasks.json` 側に
  別途残す必要はない
- `develop/progress.md` の「完了したこと」は、**新しい順に `archive.progressCount` 件、かつ
  `archive.progressBytes` 以内に収まるぶんだけを残し**、溢れたぶんを
  `docs/history/progress-archive.md` へ移す（移す先でも新しいものが上に来るよう、
  見出しの直後に差し込む）。1小節だけで予算を超える場合も、**最低1小節は残す**。
  「未解決」「注意」は移さない（未完了タスクの完了条件がこれらを参照していることがある）
- アーカイブのエントリは `## <id>` → `**タスク**: <summary の値>` → メタ行
  （`difficulty` / `loopable` / `dependencies` / `passes`）→ `**evidence**:` → `task` 本文の順
  （`**タスク**:` の行に `task` 本文の先頭を流し込まない。上の「summary」節）
- タスクIDの通し番号は再利用せず、常に続きから採番する

**転記は `scripts/archive.py` が行う。モデルが手で書き写さない。**

```bash
python3 <task-workflowスキルのディレクトリ>/scripts/archive.py develop/tasks.json
```

上の形式は `tasks.json` の値から機械的に決まり、判断が1つも要らない。手で書くと
(1) 移したぶんがそのまま出力トークンになり、(2) 書くたびに形式がぶれる（同じ運用の
プロジェクト間で `## <id>` の行に `summary` を載せる／載せないが分かれた実績がある）。
`tasks.json` と `progress.md` を独立に判定して、該当した側だけを移す。`--dry-run` を付けると
何も書かずに対象だけを報告する。

`python3` が動かない環境では**手で代用しない**。代用すると、節約の仕組みが死んでいることに
誰も気づけないまま、毎サイクル数万文字を読む状態が続く。エラーを報告してアーカイブを見送る。

### `dependencies` の扱い

- アーカイブ済みタスクのIDを指す `dependencies` は**そのまま残す**（書き換えない）
- **`develop/tasks.json` に存在しないタスクIDは「アーカイブ済み＝完了」とみなす**。
  依存解決の際は `develop/tasks.json` の `id` 一覧に無い `dependencies` エントリを
  完了済みとして扱ってよい
