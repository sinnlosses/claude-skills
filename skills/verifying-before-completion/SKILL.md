# 完了前の検証

主張は、それを証明するコマンドの出力を読んだあとにだけ言う。読んでいない出力は証拠ではなく、
「たぶん」「通るはず」「前に通った」は主張の代わりにならない。

## 関門

「完了」「修正済み」「通過」「満たした」を言う前に、毎回この順で行う。

1. **主張を1文で決める**: 「テストが通る」「落ちていた再現が直った」のように、何が真だと言いたいのかを書く。
2. **その主張を証明するコマンドを決める**: 主張が違えばコマンドも違う。下の表から引く。
3. **その場で打つ**: 全部を、いまの作業ツリーの、最後に変更したあとの状態で打つ。以前の実行・
   他のファイルの結果・一部の段だけの結果は使わない。
4. **出力と終了コードを読む**: 件数・失敗の行・終了コードを見る。出力の末尾だけで済ませない。
5. **言う**: 合っていれば、打ったコマンドと読んだ結果（終了コード、件数）を添えて主張する。
   合っていなければ、実際の状態（何が何件落ちたか）をそのまま言う。

打ったあとにファイルを変えたら、1に戻って打ち直す。

## 主張と証拠

| 主張 | 証拠 | 証拠にならないもの |
| --- | --- | --- |
| テストが通る | テストコマンドの出力が失敗0件・終了コード0 | 前回の実行、「変更が小さいので影響しない」 |
| 型検査・リンタが通る | その検査のコマンドが終了コード0 | テストが通ったこと（別の検査） |
| ビルドが通る | ビルドコマンドが終了コード0 | リンタや型検査の通過 |
| 不具合が直った | 直す前に落ちた再現を打ち直して通る | コードを直したこと自体 |
| 回帰テストが効く | 修正を戻すと落ち、入れると通る | 入れた状態で通っただけ |
| 委譲先が終わった | 差分を自分で読み、検証コマンドを自分で打つ | 委譲先の「できました」 |
| 要件を満たした | 要件の行を1つずつ、動かした結果や差分に照らす | テスト全件の通過 |

- **全段を打つ**: プロジェクトの検証コマンドが複数の段（型検査・リンタ・テスト・ビルドなど）でできて
  いるなら、全段を通した出力だけを「通った」の証拠にする。一部の段の通過を全体の通過と言わない。
- **見た目は目で確かめる**: 画面の描画に関わる変更は、コマンドの通過に加えて、実際に開いて何が
  見えたかを添える。
- コマンドの選び方・走らせる範囲・目視の手順はプロジェクトの `CLAUDE.md`（`AGENTS.md`）が決める。
  書いてあればそれに従い、ここでは関門の形だけを持つ。

## 言い訳と現実

| 言い訳 | 現実 |
| --- | --- |
| 変更が小さい・自明だ | 小さい変更の見落としは、読まれない分だけ長く残る |
| さっき通った | さっきの状態の証拠で、いまの状態の証拠ではない |
| 時間がかかる | 打たずに言った主張は、あとで人が打ち直す費用を生む |
| 一部だけ通れば同じだ | 落ちるのは打たなかった段 |
| 自信がある | 自信は出力ではない |
| 打てない環境だ | 打てなかったと言い、確かめていない範囲を明記する |

## 委譲先の報告

委譲先の「できた」は主張であって、証拠は差分と出力にある。

- 報告を読む前に差分を読み、報告が言う変更と照らす。報告に無い変更・報告にあって差分に無い変更を
  拾う。
- 検証コマンドは委譲先の出力を借りずに自分で打つ。委譲先が打った記録があっても、その後に作業
  ツリーが変わっていれば打ち直す。
- 要件は、委譲先が書いた説明ではなく依頼の元の条件に照らす。
- 照らして合わなければ、委譲先へ差分の場所と実際の出力を添えて差し戻す。
