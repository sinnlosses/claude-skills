# ADRの書式

ADRは `docs/adr/` に置き、連番を使う: `0001-slug.md`、`0002-slug.md` など。

`docs/adr/` ディレクトリは遅延的に作る: 最初のADRが必要になったときだけ作成する。

## テンプレート

```md
# {決定事項の短いタイトル}

{1〜3文: 背景は何か、何を決めたか、なぜか。}
```

これで十分。ADRは1段落だけでもよい。価値があるのは、決定が*なされたこと*とその*理由*が記録されている点であり、セクションを埋めることそのものではない。

## 任意のセクション

本当に価値がある場合のみ含める。ほとんどのADRはこれらを必要としない。

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）: 決定が見直される場合に有用
- **検討した選択肢**: 却下した代替案を覚えておく価値がある場合のみ
- **結果(Consequences)**: 自明でない下流への影響を指摘する必要がある場合のみ

## 番号付け

`docs/adr/` 内で既存の最大番号を確認し、1つ増やす。

## ADRを提案すべきタイミング

以下の3つすべてが真であること:

1. **元に戻しにくい**: 後で考えを変えるコストが無視できない
2. **文脈なしでは意外**: 将来の読者がコードを見て「なぜこんなやり方をしたんだ？」と疑問に思うだろう
3. **本物のトレードオフの結果**: 本当に別の選択肢があり、特定の理由でその1つを選んだ

元に戻しやすい決定はスキップする: どうせ元に戻すことになる。意外でなければ、誰も理由を疑問に思わない。本物の代替案がなければ、「当たり前のことをした」以上に記録すべきことはない。

### 該当するもの

- **アーキテクチャの形。** 「モノレポを使う」「書き込みモデルはイベントソーシングで、読み取りモデルはPostgresに投影する」
- **コンテキスト間の統合パターン。** 「OrderingとBillingはドメインイベント経由で通信し、同期HTTPは使わない」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、入れ替えに四半期かかるようなものだけ。
- **境界とスコープの決定。** 「顧客データはCustomerコンテキストが所有し、他のコンテキストはIDでのみ参照する」明示的な「やらないこと」も、「やること」と同じくらい価値がある。
- **意図的に自明な道から外れた選択。** 「XのためにORMではなく手書きSQLを使っている」合理的な読者が逆を想定しそうなことは何でも。これにより、次のエンジニアが意図的だったものを「修正」してしまうのを防げる。
- **コードから見えない制約。** 「コンプライアンス要件のためAWSは使えない」「パートナーAPIの契約により応答時間は200ms未満でなければならない」
- **却下が自明でない場合の却下された代替案。** GraphQLを検討して微妙な理由でRESTを選んだなら記録する。さもないと半年後に誰かがまたGraphQLを提案してくる。
