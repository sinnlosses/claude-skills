# UI のプロトタイプ

1つのルート上に、**大きく異なる UI のバリエーションを複数**作り、画面下部に浮かぶバーで切り替えられるようにする。ユーザーはブラウザ上でバリエーションを行き来し、1つを選び(あるいは各案から良いところを拾い)、残りを捨てる。

問いが見た目ではなくロジックや状態に関するものなら、この分岐は誤り。[LOGIC.md](LOGIC.md) を使う。

## この形が適しているとき

- 「このページはどんな見た目にすべきか？」
- 「このダッシュボードについて、決める前にいくつか案を見たい。」
- 「設定画面の別のレイアウトを試して。」
- 3つの曖昧なモックアップの中から選ぶのに、頭の中で丸一日を費やしそうなとき。

## 2つの副次形: 強く A を勧める

UI のプロトタイプは、**アプリの残りの部分と突き合わせる**と、はるかに判断しやすい: 本物のヘッダ、本物のサイドバー、本物のデータ、本物の密度。単独の使い捨てルートは真空で、どのバリエーションも単体なら良く見える。バリエーションを載せられそうな既存のページがありうるなら、常に副次形 A を既定にする。近くに居場所が本当にないときだけ副次形 B に手を伸ばす。

### 副次形 A: 既存ページの調整(推奨)

ルートは既に存在する。バリエーションは**同じルート上**に描画し、`?variant=` という URL の検索パラメータで出し分ける。既存のデータ取得・パラメータ・認証はそのまま残り、入れ替わるのは描画だけ。これが既定で、特別な理由がない限りこちらを選ぶ。

試作の対象にまだページはないが、*自然に何かのページの中に収まる*もの(ダッシュボードの新しいセクション、設定画面の新しいカード、既存のフローの新しいステップ)も、副次形 A である。バリエーションを受け皿のページの中にマウントする。

### 副次形 B: 新しいページ(最後の手段)

試作の対象が、収まる既存ページを本当に持たないとき(まったく新しいトップレベルの画面、どこにも自然に埋め込めないフローなど)にだけ使う。

プロジェクトが既に使っているルーティング規約に従って、**使い捨てのルート**を作る。新しいトップレベルの構造を発明しない。プロトタイプだと一目で分かる名前にする(例: パスやファイル名に `prototype` を含める)。`?variant=` の方式は同じ。

副次形 B に決める前に確認する: これを埋め込める既存のページは、本当にないのか。空のルートは、中身の詰まったルートなら露わにする設計上の問題を隠す。

どちらの副次形でも、画面下部に浮かぶバーは同一である。

## 手順

### 1. 問いを書き、N を決める

既定は **3 バリエーション**。5 を超えると大きな違いではなくノイズになり始めるので、そこで上限にする。

計画を、プロトタイプの置き場所かファイル先頭のコメントに1行で書く:

> 「設定ページの3つのバリエーション。既存の `/settings` ルート上で `?variant=` により切り替える。」

ユーザーがその場にいて反論できても、いなくても、これは機能する。

### 2. 大きく異なるバリエーションを生成する

各バリエーションを起こす。それぞれ次を守る:

- ページの目的と、使えるデータ。
- プロジェクトのコンポーネントライブラリやスタイリングの仕組み(TailwindCSS、shadcn、MUI、素の CSS など、何であれ)。
- 明確な export 名のコンポーネント。例: `VariantA`、`VariantB`、`VariantC`。

バリエーションは**構造的に違う**ものにする: レイアウト、情報の階層、主要なアフォーダンスが違い、色が違うだけではない。少しだけ手を入れた3つのカードグリッドは UI のプロトタイプではなく壁紙である。2つの案が似すぎたら、「カードグリッドを使わない」と明示的に指示して1つを作り直す。

### 3. 結びつける

ルート上に切り替え用のコンポーネントを1つ作る:

```tsx
// 擬似コード。プロジェクトのフレームワークに合わせる
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

副次形 A(既存ページ)では、既存のデータ取得はすべて切り替えの上に残し、バリエーションごとに変わるのは描画するサブツリーだけにする。

副次形 B(新しいページ)では、`/prototype/<name>` 配下の使い捨てルートが同じ切り替えをマウントする。

### 4. 浮かぶ切り替えバーを作る

画面下部中央に固定配置する小さなバーで、3つの部品から成る:

- **左矢印**: 前のバリエーションへ移る(端で折り返す)。
- **バリエーションのラベル**: 現在のバリエーションのキーを示し、バリエーションが名前を export していればそれも示す。例: `B (Sidebar layout)`。
- **右矢印**: 次へ移る(端で折り返す)。

挙動:

- 矢印をクリックすると URL の検索パラメータを更新する(フレームワークのルーターを使う。Next なら `router.replace`、React Router なら `navigate` など)。バリエーションが共有でき、リロードしても保たれる。
- キーボード: `←` と `→` でも切り替わる。`<input>`・`<textarea>`・`[contenteditable]` にフォーカスがあるときは矢印キーを奪わない。
- ページと視覚的にはっきり区別する(例: コントラストの高いピル形、控えめな影)。評価中のデザインの一部ではないと一目で分かるように。
- 本番ビルドでは隠す: `process.env.NODE_ENV !== 'production'` かそれ相当の判定で守り、プロトタイプがうっかりマージされても、バーが利用者に出ないようにする。

切り替えは1つの共有コンポーネントにまとめ、どちらの副次形からも使い回せるようにする。共有 UI を置く場所があるなら、そこに置く。

### 5. 手渡す

URL(と `?variant=` のキー)を伝える。ユーザーは手が空いたときに行き来する。得られる面白いフィードバックは、たいてい**「B のヘッダと C のサイドバーがほしい」**で、それが本当に望んでいるデザインである。

### 6. 答えを残して片付ける

勝つバリエーションが決まったら、答え(どのバリエーションを、なぜ)を残し、そのうえで [SKILL](SKILL.md) の書き方に沿ってプロトタイプ自体を残す。勝ったものを本物のコードに取り込み、残りは main ではなく、main に入れない枝に移す:

- **副次形 A**: 勝ったものを既存のページに取り込み、負けたバリエーションと切り替えを main から外す。
- **副次形 B**: 勝ったバリエーションを本物のルートに昇格させ、使い捨てのルートと切り替えを main から外す。

バリエーション一式は一次情報なので、ごみ箱ではなく、main に入れない枝に置く。main に残ったバリエーションのコンポーネントや切り替えは、すぐ腐って次の読者を混乱させる。

## アンチパターン

- **色や文言だけが違うバリエーション。** それは微調整であって、プロトタイプではない。本物のバリエーションは構造について意見が食い違う。
- **バリエーション間でコードを共有しすぎる。** 共有の `<Header>` は構わないが、共有の `<Layout>` は目的を台無しにする。各バリエーションがレイアウトを捨てられる自由を持つこと。
- **バリエーションを本物の変更処理につなぐ。** 読み取り専用のプロトタイプで構わない。バリエーションが変更を要するなら、スタブに向ける: 問いは「どんな見た目にすべきか」であって、「バックエンドが動くか」ではない。
- **プロトタイプをそのまま本番に昇格させる。** バリエーションのコードは、プロトタイプの制約(テストなし、エラー処理は最小限)のもとで書かれている。取り込むときはきちんと書き直す。
