# ロジックのプロトタイプ

誰でもボタンをクリックして状態モデルを動かせる、自己完結した HTML ファイル1枚(**共有できるデモ**)。問いが**ビジネスロジック・状態遷移・データの形**に関するときに使う。紙の上では筋が通って見えるのに、実際のケースを通してみて初めて違和感が出るような類のものである。

1ファイルで何もインストールしなくてよいので、非開発者(デザイナー、PM、ドメインの専門家)に渡して、モデルを自分で触って確かめてもらえる。だから、コードの言葉ではなく相手の言葉で語る。

## この形が適しているとき

- 「この状態機械は、X のあとに Y が起きるエッジケースを扱えているだろうか。」
- 「このデータモデルで、…というケースを本当に表現できるのか。」
- 「書く前に、API がどんな感触になるか確かめたい。」
- **ボタンを押して状態の変化を眺めたい**と誰かが思うもの全般。

問いが「どんな見た目にすべきか」なら、この分岐は誤り。[UI.md](UI.md) を使う。

## 手順

### 1. 問いを書く

コードを書く前に、どの状態モデルについてどんな問いを試作するのかを書き出す。デモの冒頭に1段落(コメントだけでなく、目に見える導入文として)。間違った問いに答える論理プロトタイプは丸ごと無駄になるので、ユーザーがいま見ている場合も、離席中に後から戻ってくる場合も、あとで確かめられるよう問いを明示する。

### 2. ロジックを持ち運べるモジュールに切り出す

実際のロジック(問いに答える部分)を、1つの `<script>` ブロックの中に、小さな純粋なモジュールとして書く。あとで取り出して本物のコードベースにそのまま落とせる形にする。周りのページは使い捨てだが、このモジュールはそうではない。

適切な形は問いによって決まる:

- **純粋な reducer**: `(state, action) => state`。操作が離散的なイベントで、状態が単一の値であるときに向く。
- **状態機械**: 明示的な状態と遷移。「いま合法な操作はどれか」が問いの一部であるときに向く。
- **プレーンなデータ型に対する小さな純粋関数の集まり**。暗黙の現在状態がなく、変換だけがあるときに向く。
- **明確なメソッドの面を持つクラスやモジュール**。ロジックが本当に内部状態を持ち続けるとき。

ページに結びつけやすい形ではなく、問われていることに最も合う形を選ぶ。純粋に保つ: DOM も `document` もなく、ボタンのハンドラが中に手を伸ばすこともない。ページがモジュールを呼び、逆向きには何も流れない。これがプロトタイプの寿命を超えて役に立つ理由で、問いに答えが出たら、検証済みの reducer・機械・関数群がそのまま本物のモジュールに持ち上がる。

### 3. 共有できる HTML ファイルを作る

プレーンな HTML/CSS/JS の1ファイル: フレームワークなし、バンドラなし、サーバなし、すべてインラインで、ダブルクリックで開け、メールで回しても壊れない。開くだけで誰でも動かせるようにする。

非開発者向けに書く。ラベルはすべて、コードの言葉ではなく**ドメインの言葉**にする: ボタンや状態は reducer ではなく業務のように読める。何が起きているかを平易な言葉で説明する。

上から下へ、きれいな階層で並べる:

1. **タイトルと1行の説明**: このデモで何を探れるか(手順1の問い)。
2. **現在の状態**: 関係する状態の全体を、読めるパネル(生の JSON のダンプではなく、ラベル付きのフィールド)として描画し、クリックのたびに再描画して変化が見えるようにする。非開発者が追いやすくなるなら、いま何が変わったかを強調する。
3. **自由に押せるボタン**: 操作ごとに1つのボタンを、常に押せる状態で置き、誰でも好きな順序でモデルを突いてみられるようにする。クリックするとその操作を dispatch して状態を再描画する。
4. **ガイド付きの手順**: **シナリオ**の集まりで、1つにつき1タブ。各タブには、シナリオの短い平易な説明(設定する状況と、注目すべき点)があり、その下にそのシナリオで**押すべきボタン**が順番に並ぶ。各ステップは本物のボタンで、クリックするとその操作を実行して次のステップに進む。手順を始めると既知の初期状態にリセットされ、シナリオが毎回同じように走る。

シナリオは、紙の上では考えにくい厄介なケースを見せるものを選ぶ: 正常系、トリッキーなエッジケース、本来は不正なはずの操作を試みるもの。

美しく、しかし控えめに: すっきりした書体、ゆとりのある余白、アクセントカラーは1色。アニメーションなし、小細工なし。状態とボタンの邪魔をするものを置かない。

### 4. 手渡す

ファイルを送るか、開いてあげる。相手は手が空いたときに手順や自由操作をクリックして試す。面白いのは、「待って、そんなことが起きていいの？」「あれ、X は違うと思っていた」と言われる瞬間で、それが*アイデア*のバグであり、それこそが目的である。新しい操作やシナリオを求められたら足す。プロトタイプは育てていくもの。

### 5. 答えとプロトタイプを残す

プロトタイプが問いに答えたら、答えを残し、そのうえで [SKILL](SKILL.md) の書き方に沿ってプロトタイプ自体を残す。ロジックの場合の対応: 検証済みの reducer・機械・関数群は本物のモジュールに持ち上げ(決定が取り込まれる)、HTML の殻は、プロトタイプを一次情報として残す、main に入れない枝へ一緒に載せる。1ファイルで自己完結しているので、そこでもそのまま再実行できる。

## アンチパターン

- **テストを足さない。** テストが要るプロトタイプは、もうプロトタイプではない。
- **本物のデータベースにつながない。** 問いが永続化そのものについてでない限り、メモリ上の状態を使う。
- **一般化しない。** 「あとで X に対応したくなったら」は不要。プロトタイプが答えるのは1つの問いだけ。
- **ロジックとページを混ぜない。** 純粋なモジュールが DOM や `document`、ボタンのハンドラを参照したら、もう取り出せない。ページは純粋なモジュールの上に載る薄い殻に保つ。
- **フレームワーク・バンドラ・サーバに手を出さない。** 受け取った人がダブルクリックするファイル1枚。React アプリや開発サーバは「共有できる」を台無しにする。
- **HTML の殻を本番に出さない。** ページは手で順にクリックされることに最適化されている。残す価値があるのは、その裏にあるロジックのモジュールのほう。
