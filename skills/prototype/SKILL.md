# プロトタイプ

プロトタイプとは、**問いに答えるための使い捨てコード**である。問いが形を決める。

## 分岐を選ぶ

ユーザーの依頼、周辺のコード、あるいはユーザーがその場にいれば質問によって、どの問いに答えようとしているのかを特定する:

- **「このロジック / 状態モデルは妥当か？」** → [LOGIC.md](LOGIC.md)。紙の上では判断しづらいケースまで状態機械を押し込み、非開発者でも操作できる、共有可能な HTML ファイル1枚（自由に押せるボタンと、タブ分けされたガイド付きの手順）を作る。
- **「これはどんな見た目にすべきか？」** → [UI.md](UI.md)。1つのルート上に、大きく異なる UI のバリエーションを複数作り、URL の検索パラメータと画面下部に浮かぶバーで切り替えられるようにする。

2つの分岐はまったく違う成果物になるので、選び間違えるとプロトタイプ全体が無駄になる。問いが本当に曖昧でユーザーに連絡がつかないなら、周辺のコードにより合うほうを既定にし（バックエンドのモジュールならロジック、ページやコンポーネントなら UI）、その仮定をプロトタイプの冒頭に明記する。

## 両方に共通する規則

1. **最初から使い捨てで、そうと分かるようにしておく。** プロトタイプのコードは、実際に使われる場所の近く（試作の対象であるモジュールやページの隣）に置いて文脈が分かるようにしつつ、通りがかりの読者が本番コードではなくプロトタイプだと分かる名前にする。使い捨ての UI ルートは、プロジェクトが既に使っているルーティング規約に従う。新しいトップレベルの構造を発明しない。
2. **起動が自明。** UI のプロトタイプは、プロジェクトのタスクランナーの1コマンドで始まる: `pnpm <name>`、`python <path>`、`bun <path>` など。ロジックのデモは、ユーザーがダブルクリックする HTML ファイル1枚。どちらも、始めるのに考える必要がない。
3. **既定では永続化しない。** 状態はメモリに置く。永続化はプロトタイプが*確かめる対象*であって、依存するものではない。問いが明確にデータベースに関わるなら、「PROTOTYPE, wipe me」と分かる名前の捨てても構わない DB かローカルファイルを使う。
4. **仕上げを省く。** テストなし、*動かす*のに要る以上のエラー処理なし、抽象化なし。目的は素早く何かを学ぶこと。
5. **状態を見せる。** 操作のたび（ロジック）、またはバリエーションの切り替えのたび（UI）に、関係する状態の全体を出力または描画して、何が変わったか見えるようにする。
6. **終わったら残す。** 検証できた決定は本物のコードに取り込み、そのうえでプロトタイプ自体を**一次情報**として残す: main に入れない枝にコミットし、その枝名を、実装のタスク（task-workflow の課題）や `develop/draft/` の指示メモに書いて文脈の手がかりにする。答え（評決と、それが決着させた問い）もタスクかコミットに残す。main に残るのは検証できた決定だけにする。
