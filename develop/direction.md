# 未対応の指示メモ（エージェントのドラフトは develop/draft/ に1件1ファイル）

## ユーザーから

- /next-task の1件の中をパイプラインにして速くしたい（2026-10-07 利用者）。ワークフローはタスクの中で完結させ、次のタスクの計画を先に立てるような件をまたぐ並列はしない。次の2つを入れる:
  - 受け入れの順を「レビュー（差し戻しの往復まで）→ 振り返り と 送る前の検証 を並べる」にする。振り返りは、レビューで差し戻した指摘を lint に落とすような候補を拾えるので、レビューの結果を待ってから行う。送る前の検証（`tw verify` が送る前の検証コマンドで打って控えを取る）は振り返りと同時に背景で走らせ、`tw ship` がその控えで検証を省けるようにする。振り返りが `develop/draft/` に積むドラフトや `tw done` の書き込みで検証の控えが外れ、ship で打ち直しにならないかを確かめ、外れるなら控えの鍵か順番で手当てする。`tw metrics --stages` の段の数え方（`retro` の `lap` と検証が重なる）も合わせて直す
  - 段の並列は計画で決める。`## やること` を書くとき（登録時の /plan-tasks と、書き直しから委譲する回）に、段ごとにどの段のあとに走れるか（並列にできるか）を書く欄を段の形に足す。/next-task は並列にできる段を別々のサブエージェントで同時に起こし、合流してから `tw verify` を1回打つ（今の `parallel-docs.md` の文書の担当はこの形に畳む）。並列と書いた段どうしが触るファイルを重ねていないかは `tw plan-check` が機械的に確かめ、重なれば並列を外して1本道で進める。並列の段のそれぞれの返却・`tw step`・`handback-guard` の扱いと、段ごとの所要の記録（`flow` の重なり）も決める。段の進みを tsukumo などの表示側へ渡す口はスキルの側では決めず、表示側が定める口に従う
