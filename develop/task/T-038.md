## 目的・背景

`/next-task` の委譲先は「最初に `## やること` を書いて `tw edit` で渡す」よう指示されている。T-032 で
`skills/task-workflow/scripts/task.py` の `cmd_edit` が、作業ツリーに差分がある状態での記入に
`PLAN_AFTER_WORK` を出すようになり、受け入れでは `cmd_plan_check` が `PLAN_NOT_FIRST after-work` を出す。
それでも T-034 で委譲先が作業の後に書いた（警告は作業の後に出るので、順を戻す手段にならない）。
札「黄 制約違反」は tsukumo の GH-92 に続いて2回目で、文章の指示と事後の警告では防げていない。
振り返りのドラフト `develop/draft/2026-09-29-plan-first-gate.md`（承認済み）。

## 決まっていること（蒸し返さない）

- 警告だけで済ませず、順を守らないと先へ進めない関門を `tw`（`task.py`）に置く
- ファイル方式と Beads 方式の両方で同じ出力の形にする（`plan-check` と同じ扱い）

## 解くべき論点

- 関門をどこに置くか: (a) `## やること` が空のうちは `tw verify` が通らない（例: `VERIFY_NOT_PASSED` と理由 `PLAN_MISSING`）、(b) claim 以降に作業ツリーの差分がある状態での初回記入を `tw edit` が拒む、(c) その両方。(b) は拒んだあとに正しい順へ戻す手段（差分を退けずに書かせる方法）が要る。`git stash` は委譲先に禁じている
- 関門に掛かったとき委譲先に何をさせるか（出力の文面で次の一手が分かるようにする）
- 受け入れの `plan-check` と `/next-task` の手順6の表・正典「`tw` コマンドの参照」の終了コード・先頭語の表との整合

## やること

前提の確認（いまのコード）: `task.py` の `cmd_edit`（ファイル方式）と `cmd_beads_edit` は、着手の印の持ち主が `## やること` に初めて中身を入れたとき `_plan_state` で `first`／`after-work` を判定し、`after-work` なら書き込んだうえで `EDITED` の次に `PLAN_AFTER_WORK` の行を出す（終了コード0）。`cmd_plan_check`・`cmd_beads_plan_check` は `PLAN_NOT_FIRST\tT-xxx\tafter-work` を出す。`cmd_verify` はタスクを見ずに検証コマンドを打つ。`selftest_task.py` の「edit・plan-check」の節は `test_edit_and_plan_check`。振り返りのドラフトは T-038 の登録で `develop/draft/` から外れている（`git show b310935^:develop/draft/2026-09-29-plan-first-gate.md` で中身を確かめた）。T-034 では委譲先が作業と `tw edit` を同じ手でまとめて打っていた。

論点への答え: (c) 両方を置く。
- (b) `tw edit` の関門: 着手の印の持ち主が `## やること` に初めて中身を入れるとき、作業が始まっていれば（`_plan_state` が `after-work`）書き込まずに `WORK_BEFORE_PLAN\tT-xxx\t<次の一手>` を出して終了コード4。戻す手段は `--after-work` を付けて打ち直すこと（差分は退けない。印は `after-work` のまま正直に残り、`EDITED` と `PLAN_AFTER_WORK` の行が出る）。`--after-work` は作業が始まっていないときは何も変えない（印は実際の順で決まる）。作業と同じ手でまとめて打つと最初の一手で拒まれるので、順の誤りに作業の入口で気づける
- (a) `tw verify` の関門: この作業ツリーが印を持つ着手中のタスク（ファイル方式は作業ツリーのタスクファイルが `todo`・`hold`、Beads 方式は `in_progress` で `task done` の印が無いもの）の `## やること` が空か「なし」で、かつ作業が始まっていれば、検証コマンドを打たずに控えを消し、`PLAN_MISSING\tT-xxx\t<次の一手>` を出して終了コード10（`VERIFY_NOT_PASSED` と同じく「直して打ち直す」）。`VERIFY_NOT_PASSED` の2列目はログのパスなので、形を崩さないよう先頭語を分ける。(b) だけだと `## やること` を書かずに終える抜け道が残るので、書かずには検証を通せないようにする
- 正当な流れを壊さない範囲: 作業が始まっていない（差分もコミットも無い）ときは (a) も (b) も掛からないので、前提が崩れて作業せずに `dropped` を報告する流れは変わらない。`loopable: N` でメインが進めるときは印の持ち主がメインになるだけで、同じく先に書けば掛からず、後なら `--after-work` で書ける。`tw done` の後（status が `done`・`dropped`、Beads は `ship:` の印）は (a) の対象外なので、受け入れの順（`done` の後に `verify`・`ship`）で詰まらない。印の無い作業ツリー・`plan-tasks` の `edit`・着手前の Beads の `hold`↔`todo` にも掛からない
- 受け入れとの整合: `plan-check` の出力は変えない。手順6の表の `missing`・`unrecorded` の行でメインが `tw edit` で直すときは作業の後なので `--after-work` を付ける、と書く

作業:
1. `task.py`: `edit` に `--after-work` を足し、`cmd_edit`・`cmd_beads_edit` を関門に変える。`cmd_verify` に着手中の自分のタスクで `## やること` が空かつ作業が始まっているものを返す関数（ファイル方式・Beads 方式それぞれ）を渡し、あれば `PLAN_MISSING` で止める
2. `selftest_task.py`: 「edit・plan-check」の節に、作業の後の初回記入が拒まれて書き込まれない・`--after-work` で書ける・作業前なら掛からない、と、`verify` が空のまま作業があると `PLAN_MISSING`（検証コマンドを打たない）・作業が無ければ／書いてあれば／`done` の後なら打つ、を足す。`selftest_beads.py` に Beads 方式の同じ場合を足す（既存の edit・plan-check のテストに沿う）
3. `WORKFLOW.md` の「`tw` コマンドの参照」の `edit`・`verify` の行と終了コードの表（4 に `WORK_BEFORE_PLAN`、10 に `PLAN_MISSING`）、Beads 方式の `edit` の行を直す
4. `next-task/SKILL.md` の委譲の指示（`tw edit` は単独で打つ・拒まれたら `--after-work`・`PLAN_MISSING` の扱い）と手順6の表を直す
