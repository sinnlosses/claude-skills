## 目的・背景
いまの `/next-task` は `loopable: Y` なら色1つの変更でも、計画・委譲・検証・受け入れのレビュー・振り返り・送り出しを全部通り、中身の作業より段の出入りのほうが長い（利用者の指示）。基準に当たるタスクはメインが自分で直し、検証と送り出しだけを通す「委譲しない近道」を作る。基準そのものは、T-043・T-044 の段ごとの所要時間の記録を見て見直せる形にする。

いま: `skills/task-workflow/WORKFLOW.md` の「difficulty とモデルの切り替え」は「一致していても委譲する——理由はモデルではなく文脈の隔離」「委譲しないのは `loopable: N` に当たるときだけ」「`haiku` を例外にしないのは…『これは例外か』の判断が毎回1つ増えるため」と書く。近道はこの方針を変える。`skills/next-task/SKILL.md` で委譲しない道は `loopable: N` の `main-run.md` だけ。タスクの front matter（`skills/task-workflow/scripts/taskfile.py`）と `tw new` の引数（`skills/task-workflow/scripts/task.py` の `p_new`）に近道の印は無い。

## 決まっていること（蒸し返さない）
- 近道に当たるかは**登録時に `/plan-tasks` が決めて印を付け**、`tw` が機械で測れる条件を検査する。`/next-task` は印を見るだけで、着手時に「これは近道か」を判断しない（利用者が選んだ。正典が挙げた「判断が毎回1つ増える」を避けるため）
- 登録時に人（`/plan-tasks`）が見る条件: 振る舞いの契約（公開の出力・引数・終了コード・正典の規則）を変えない。`tw` が機械で見る条件: `difficulty` が `haiku`、`## やること` の段が1つ、`### 名指すファイル` が少ない（数のしきい値は論点）
- 近道で通すのは、`## やること` に沿ったメインの直し・`tw verify`・`tw done`・コミット・`tw ship`。委譲・受け入れのレビュー・振り返り（手順6a）は通らない
- 基準の値（しきい値）は正典の1か所（WORKFLOW.md の表）とそれを読むコードの定数にだけ置き、週ごとの振り返りが `tw metrics --stages` の近道と通常の比較から見直せるようにする
- 近道で進めたタスクは flow の記録で通常と見分けられる

## 解くべき論点
- 印の持ち方: front matter の欄（例 `direct: Y`）か別の形か。`tw new`・`tw edit`・`tw adopt` の引数、Beads 方式での置き場（`skills/task-workflow/scripts/beads.py` の `to_task` が読める形）
- `tw` の機械検査をどこで掛けるか: 登録時（`tw new` が条件を外れた印を終了コード2で拒む）だけか、着手時（`tw claim` か `tw plan-check` の出力に近道かを出す）にも掛けるか。登録のあとに `tw edit` で段や `difficulty` が変わったときの扱い
- `### 名指すファイル` の数のしきい値と、「差分が数行」をどう扱うか（直したあとの差分が大きくなったら近道を降りて通常の委譲に戻すか、記録だけ残すか）
- flow で近道を見分ける形（`claim` に欄を足すか、T-043 の `lap` に段を足すか）と、`tw metrics --stages` で近道と通常を分ける欄
- 近道で `## 結果` の `- 振り返り:` 行をどう書くか（`tw done` の `reflection` の記録と `reflection_none_ratio` を歪めない形）
- `/loop` での文脈の隔離: 近道が積み上げるメインの文脈の量をどう抑えるか（正典の委譲の実測の段落との整合）

## やること
### 1. 印と機械検査を `tw` に足す
`skills/task-workflow/scripts/taskfile.py` に印の欄、`skills/task-workflow/scripts/task.py` の `new`・`edit`・`adopt` に印の引数と機械検査（論点で決めた条件としきい値。定数は1か所）、着手時に近道かを出す出力を足す。Beads 方式は `skills/task-workflow/scripts/beads.py` で同じ印を読み書きする。flow に近道の区別を残し、`skills/task-workflow/scripts/metrics.py` の `--stages` で近道と通常を分ける。`skills/task-workflow/scripts/selftest_task.py`（と Beads なら `selftest_beads.py`）に自己テストを足す。
### 2. 正典を直す
`skills/task-workflow/WORKFLOW.md` の「difficulty とモデルの切り替え」の委譲の規則と `haiku` を例外にしない段落を、近道の例外（基準の表・しきい値・基準を見直す手がかり）に合わせて直す。「タスクファイル」の front matter と「`tw` コマンドの参照」の `new`・`edit`・`adopt`・着手時の出力の行に印を足す。
### 3. `/next-task` に近道の道を足す
`skills/next-task/` に近道の手順のファイル（例 `direct-run.md`）を新しく置き、`skills/next-task/SKILL.md` の手順5で印のあるタスクはそこを読んで従う（委譲・手順6のレビュー・手順6aを飛ばし、`tw verify` → `tw done` → コミット → `tw ship`）と書く。T-043 の `tw lap` の打ち方と食い違わないようにする。
### 4. `/plan-tasks` で印を付ける
`skills/plan-tasks/SKILL.md` の手順4（書く）と手順5（`tw new` の例）に、近道の条件に当たるときに印を付けることと、人が見る条件（振る舞いの契約を変えない）を書く。
### 5. 後段の本文を合わせる
論点の結論で T-043・T-044 の記録・集計の形を変えたなら、変えたことを WORKFLOW.md と `retrospect` の「週ごとに振り返る」の観点「段の所要時間」の出し先に反映する。

## 完了条件
- 登録時に近道の印を付けられ、`tw` が機械で測れる条件（`difficulty`・段の数・名指すファイルの数）を外れた印を拒む（自己テストで確かめる。Beads 方式も）
- 印のあるタスクを `/next-task` が委譲・受け入れのレビュー・振り返りを通らずに、`tw verify`・`tw done`・`tw ship` で送る手順が `skills/next-task/` にあり、SKILL.md の手順5から指されている
- WORKFLOW.md の「difficulty とモデルの切り替え」が近道の例外と基準の表を持ち、基準の値が1か所にある
- 近道で進めたタスクが flow で見分けられ、`tw metrics --stages` で近道と通常を分けて見られる
- `plan-tasks` の SKILL.md が、印を付ける条件（人が見る条件を含む）を書いている
- `./check.sh --full` が通る
