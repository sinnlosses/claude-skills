## 目的

アーキテクチャの入口が2つ（`architecture-proposal` と `improve-codebase-architecture`）に
なるので、どちらを呼ぶのかが本文から分かるようにする。分担が書かれていないと、同じ相談に
違うスキルが当たり、成果物の置き場も変わる。

## 完了条件

- `skills/architecture-proposal/SKILL.md` の「## 他のスキルとの分担」表に
  `improve-codebase-architecture` の行があり、frontmatter の `description` 末尾の
  「…は `codebase-design`、…は `domain-modeling` に任せる」と食い違わない
- `skills/improve-codebase-architecture/SKILL.md` に、様式とディレクトリ構造は
  `architecture-proposal` の領分だと書いた1〜2行がある
- `skills/architecture-proposal/SKILL.md` 手順1の「いま痛んでいる兆候」7項目について、
  残す・移す・参照に替えるのどれかを選んだ結果が本文に出ている（二重化を残す判断なら、
  なぜ両方に要るかを1行書く）
- `./check.sh` が通る

## 背景

- `skills/architecture-proposal/SKILL.md` の末尾「## 他のスキルとの分担」に4行の表があり、
  `codebase-design`・`domain-modeling`・`grilling`・`code-review` を挙げている。ここに
  新しいスキルの行が無い
- 同 SKILL.md 手順1の末尾「いま痛んでいる兆候」7項目（小さなファイルを跳ね回る／約束が
  コメントにしかない／境界を差し替えられない／切り出された関数が複雑さを隠すだけ／同じ定数が
  2箇所／置き場所が規約なしに決まらない／正典どうしで層の定義が食い違う）は、原文
  `improve-codebase-architecture` の explore の問い（shallow なモジュール・跳ね回り・
  テストのための抽出・シームからの漏れ）と重なる
- トリガーの衝突は無い。新しいスキルは `disable-model-invocation: true` で明示の呼び出し専用
  なので、`description` を削り合う必要は無く、本文の分担だけの話になる

## やること

- 前提を確認し直した結果: `## 背景` の記述どおり、`architecture-proposal` の
  「## 他のスキルとの分担」表に `improve-codebase-architecture` の行が無いこと、
  同スキルの手順1「いま痛んでいる兆候」7項目のうち3項目
  （小さなファイルを跳び回る／テストのための抽出／境界を差し替えられずテストが本物を要る）が
  `improve-codebase-architecture` の explore の問いと重なっていることを確認した。前提は崩れて
  いないので、作業を行う
- `skills/architecture-proposal/SKILL.md`「## 他のスキルとの分担」表に、既存の1行目
  （`architecture-proposal` 自身の行）の直後へ `improve-codebase-architecture` の行を足す。
  「やること」列は「既存モジュールの深化（浅いモジュールを深くする）機会をスキャンし、
  HTML レポートで比較して選ばせる（明示呼び出し専用の別の入口）」とし、frontmatter の
  `description` 末尾（「個々のモジュールの深さやインターフェースの設計は `codebase-design`、
  用語の整理は `domain-modeling` に任せる」）とは領分が異なる（`architecture-proposal` は
  様式・木を先に決める入口、`improve-codebase-architecture` は既存コードの深化を後から洗う
  別の入口）ため食い違わない
- 「いま痛んでいる兆候」7項目は**7項目とも残す**（書き換えない）。うち3項目
  （小さなファイルを跳び回る／テストのための抽出／境界を差し替えられずテストが本物の
  プロセスやネットワークを要る）は `improve-codebase-architecture` の explore の問いと重なるが、
  二重化を残す。理由を7項目の直後に1行で足す: ここでの兆候は様式・ディレクトリ構造を選ぶ根拠
  として一度きり集めるものであり、`improve-codebase-architecture` 側は個々のモジュールを
  深化候補として都度スキャンし直すための問いで、集める目的・頻度・出力形式（提案書の根拠 vs
  HTML レポートの候補）が違うため。残る4項目（約束がコメントにしかない／同じ定数が2箇所／
  置き場所が規約なしに決まらない／正典どうしで層の定義が食い違う）には
  `improve-codebase-architecture` 側に対応する項目が無いので、変更せずそのまま残す
- `skills/improve-codebase-architecture/SKILL.md` の冒頭（本文1行目の直後）に、様式と
  ディレクトリ構造全体を決めるのは `architecture-proposal` の領分であり、このスキルは
  既存モジュールの深化だけを扱う旨の1〜2行を足す
- `README.md`「## docs/ の育て方」には足さない（`improve-codebase-architecture` は `docs/` に
  書かないため、既定どおり）

## 注意

- 分担の軸にできる違い: `architecture-proposal` は様式とディレクトリ構造を扱い
  `docs/architecture-proposal.md` に提案書を残す。`improve-codebase-architecture` は
  モジュールの深さを扱い、一時ディレクトリの HTML に出して残さない
- `README.md`「## docs/ の育て方」の梯子には足さないのが既定（新しいスキルは `docs/` に
  書かないため）。足す判断をしたときだけ1行足す
- 既存スキルの手順そのものは書き換えない。足すのは分担の記述と、二重化の扱いの判断だけ
