## 目的・背景
T-040 で ID を読むところが Jira のキー（`PROJ-123`）を受けるようになったあと、実際に Jira から取り込んだ課題の
ID を Jira のキーにする。github 方式で取り込んだ課題を `external_ref` の番号の `gh-<n>` へ付け替えているのと同じことを
jira 方式でもする。

今の jira 方式（`skills/task-workflow/WORKFLOW.md` の「Beads 方式」の「Jira の方式との違い」の表）:

- タスクIDは `tw` の採番（`T-123`）で、Jira のキーは `external_ref` に入るだけ
- `tw sync` は `bd jira sync --pull` だけ（`skills/task-workflow/scripts/tracker.py` の `_jira_pull`）
- 振り分け前の課題は `tw adopt` が番号を振る（`skills/task-workflow/scripts/task.py` の adopt の処理、
  `ADOPTED\t<元のID>\t<ID>`）
- github 方式の付け替えは `tracker.py` の `external_ref` の番号と ID が違う課題を `bd rename` する処理
  （`_ref_number`・`ISSUE_URL`）

## 決まっていること（蒸し返さない）
- ID の形は T-040 の結論に従う（Jira のキーだけ。Beads の中は小文字）
- ローカルで `tw new` した課題は `T-xxx` のまま混在させる。Jira へは書かない（取り込みだけ）
- 本物の Jira では試さない。自己テストと手元の `bd`（1.3.0）で確かめられる範囲で作る

## 解くべき論点
- `bd jira sync --pull` が取り込んだ課題の ID と `external_ref` の形（キーそのものか、`https://<site>/browse/PROJ-123` か）。
  `bd` の help・ソース・手元での再現で確かめる
- Beads の `issue_prefix`（今は `t`）と違う接頭辞の ID へ `bd rename` できるか。できなければ
  別の手（`description` の末尾にキーを残して ID は変えない等）に倒すか、`dropped` で閉じる
- 付け替えの時点: `tw sync` の取り込みの直後か、`tw adopt` のときか。`jira_close`・`jira-closed` の引数も新しい ID で通ること
- 既に `T-xxx` で取り込み済みの課題を付け替えるか（切り替えの手順として正典に書くか）

## やること

前提の確かめ（`bd` 1.3.0、HOME・XDG を一時ディレクトリに向け、Jira は 127.0.0.1 の偽の HTTP サーバ）:
- `bd jira sync --pull` が作る課題の ID は `issue_prefix` の hash（例 `t-aby`。数字だけの `t-456` にもなりうる）、
  `external_ref` は `<jira.url>/browse/PROJ-123`（キーそのものではない）
- `issue_prefix` が `t` でも `bd rename t-aby proj-123` は通る（依存・comment が付いてくる。行き先があれば
  `issue proj-123 already exists` で落ちる。大文字の `PROJ-9` は形式違いで落ちる）
- 付け替えたあとの `bd jira sync --pull` は `external_ref` で同じ課題に当て、`proj-123` を更新する（二重にしない。label は残る）
- 目的・背景の場所（WORKFLOW.md の表、`tracker.py` の `_jira_pull`・`_rename`・`_ref_number`・`ISSUE_URL`、
  `task.py` の adopt の「番号でなければ振る」）は実物どおり。`dropped` にする理由は無い

決めた案:
- 付け替えの時点は取り込みの直後（`_jira_pull` の成功のあと。`tw sync` と、各操作のあとの取り込みの両方）。
  対象は `external_ref` が Jira のキー（`…/browse/<キー>` か、キーそのもの）で ID がキーの小文字と違い、
  振り分け前（`difficulty`・`loopable` の label が無い）の課題。行き先が既にあれば付け替えず
  `TRACKER\tINVALID\t<ID>\t<行き先> が既にある（付け替えない）`、`bd rename` が落ちても `INVALID` の行
- `tw adopt`（jira）: キーのある課題は番号を振らず、ID がキーでなければキーへ付け替えてから label を付ける。
  付け替えられなければ `INVALID` の行を出して終了コード3（番号は振らない）。キーの無い課題は今までどおり番号を振る
- 既に `T-xxx` で adopt 済みの課題（label あり）は自動では付け替えない（作業ブランチ・コミットの件名が
  `T-xxx` を指す）。正典の「切り替え」に、人が立ち会って未完了のものを `bd rename` する手順を書く。
  振り分け前のまま残っている取り込み済みの課題は、次の `tw sync` で付け替わる
- `jira_close`・`jira-closed` は `external_ref` と ID の読み（T-040）で新しい ID のまま通る。自己テストで確かめる
- T-040 の申し送り (2)（`ID_SEARCH_PATTERN` が `UTF-8`・`SHA-256` を拾う）は付け替えと別の、retrospect の
  検索の精度の話なので本タスクでは扱わない（報告に書く）

手を入れるところ:
- `skills/task-workflow/scripts/tracker.py`: Jira のキーの読み取りと付け替えの関数、`_jira_pull` のあとに付け替え
- `skills/task-workflow/scripts/task.py`: adopt の jira の分岐
- `skills/task-workflow/scripts/selftest_beads.py`: 偽の `bd jira sync` が課題を作れるようにし、取り込み・
  付け替え（依存・comment が保たれる、数字だけの hash、行き先が既にある `INVALID`、label のある `T-xxx` は
  触らない）・adopt（番号を振らない・付け替える）・`jira_close`／`jira-closed` の例を足す
- `skills/task-workflow/WORKFLOW.md`: ID の段落、「サイクルで変わるところ」の振り分け前、トラッカーの表、
  「Jira の方式との違い」の表、切り替え、adopt の行
- 検証: `tw verify`（`./check.sh`）
