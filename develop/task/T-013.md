## 目的

主ブランチ名が `main` に固定されているのをやめ、`master`・`trunk` のリポジトリでも
`task` コマンドが動くようにする。

## 完了条件

- `skills/task-workflow/scripts/ledger.py` に `base_branch(cwd)` があり、`task.py`・`ship.py` が
  git に渡す枝名をすべてそれ経由で得ている
- `grep -nE '"main"|main\.\.HEAD|refs/heads/main' skills/task-workflow/scripts/task.py skills/task-workflow/scripts/ship.py`
  が、コード（git の引数・比較）としては0件（コメント・docstring の説明文は対象外）
- `selftest_task.py` の足場が枝名を引数で受け、**主ブランチが `master` のリポジトリで一式を
  通すケースが1本ある**（足場が `main` のままなら汎用化できたことにならない）
- `./check.sh` が通る

## 背景

git に渡す引数としての `main` は `skills/task-workflow/scripts/task.py` に15行、`ship.py` に5行、
`selftest_task.py` の足場に13行ある。

- `task.py:65` `ls-tree --name-only -r main -- develop/task`、`:72` `show main:develop/task/<file>`、
  `:77` `show main:docs/history/tasks.md`
- `task.py:388-393` `claim` の追い付き（`branch != "main"`・`rev-list --count main..HEAD`・
  `merge --ff-only main`）、`:426` `checkout -b feature/T-xxx main`
- `task.py:518-592` `ship` の後始末（`branch == "main"`・`rev-parse main` を2回・降りる先の
  `targets` に `"main"`・`checkout -q --detach main`）
- `ship.py:57` `find_main_worktree`（`w.branch == "main"`）、`:79` `merge-base --is-ancestor main HEAD`、
  `:81` `rebase main`、`:108-109` `rev-parse main` と `update-ref refs/heads/main`

`ledger.py` には `current_branch`・`git_toplevel`・`list_worktrees` と git を叩く関数が揃っているので、
枝名を決める関数もここに置く。

適用中の5リポジトリ（claude-skills・tsukumo・Git-Bulk-Maestro・gitlab-watari-dori・helm-yadokari）は
**すべて主ブランチが `main`**。よって既存リポジトリの挙動は変わらないことが期待値で、変わったら
それは不具合。

## 決まっていること（蒸し返さない）

決め方の順はこれにする:

1. 設定ファイルの `- 主ブランチ:` 行があればそれ（**任意行**。保護ブランチや複数リモートの逃げ道）
2. `git symbolic-ref --short refs/remotes/origin/HEAD` の枝名
3. `main`・`master`・`trunk` のうち `git rev-parse --verify` で**実在する**もの
4. どれも無ければ `INVALID`（終了コード3）。**黙って `main` を作らない**

## 解くべき論点

- `ship.py:108-109` の `update-ref refs/heads/main <head> <seen_main>`（見たときから動いていたら
  失敗する比較付き更新）を枝名可変にしたとき、他の作業ツリーとの競合検知が変わらないか
- `find_main_worktree` の名前と、`task.py:582` の降りる先の決め方（`back` → 主ブランチ →
  detached）を枝名可変にしたときの表記
- `base_branch()` を毎回 git に問い合わせるか、1プロセスで1回だけ求めて覚えるか
  （`task status` は1回の実行で何度も枝名を要る）
- 順2で `origin` が無く別名のリモート（`upstream` など）しか無いリポジトリのとき、順3へ落ちるか、
  そのリモートの HEAD を見るか

## やること

いまのコードを読み直した結果（`## 背景` との差）:

- git の引数としての `main` は `task.py` に**15行**（`## 完了条件` の grep に当たるのは13行で、
  `:72` `show main:develop/task/<file>`・`:77` `show main:docs/history/tasks.md` はその grep に
  当たらないが git の引数なので同じく直す）、`ship.py` に5行
- `selftest_task.py` の足場は `make_repo(tmp, branch, verify)` が `git init -b main`・
  `worktree add … main` を、`_no_merge_commits(repo)` が `log --merges main` を持つ
- `ledger.py` に主ブランチを決める関数は無く、`main` はモジュール冒頭の説明文だけ
- このリポジトリの `origin/HEAD` は `origin/main` を指すので、順2で `main` に決まる（挙動不変）
- `- 主ブランチ:` 行を足しても `init.py` の `check_claude_md` と `check_docs.py` の検査5は
  3行しか見ないので、`MISSING_LINE` にはならない（追加の手当ては不要）

手順:

1. `ledger.py` に `base_branch(cwd=None)` を足す。順1〜4（`## 決まっていること`）を実装し、
   どれも無ければ新しい例外 `NoBaseBranch` を投げる。CLAUDE.md の
   `- 主ブランチ:` は値の先頭語をバッククォートと句読点を落として読む（`- ブランチ:` と同じ流儀）。
   **1プロセスで1回だけ git に問い合わせて覚える**（`task status` が何度も要るので。
   キーは `git_toplevel`。テスト用に `clear_base_branch_cache()` を添える）
2. 順2は `origin` だけを見る。別名のリモートしか無いリポジトリは順3へ落とし、
   当てにならない推測（唯一のリモートを `origin` 扱いする等）はしない。逃げ道は順1の行
3. `ship.py`: `find_main_worktree` → `find_base_worktree(worktrees, own_path, base)`、
   `attempt(toplevel, base_worktree, verify_command, base)`。`merge-base`・`rebase`・`rev-parse`・
   `update-ref refs/heads/<base>` を引数の枝名にする（比較付き更新は同じ1つの名前で
   `rev-parse` と `update-ref` を行うので、競合検知は変わらない）
4. `task.py`: `_list_main_task_filenames`・`_read_main_task_text`・`_history_ids_at_main` と
   `cmd_claim`・`cmd_ship`・`_leave_feature_branch` が `ledger.base_branch(toplevel)` から枝名を得る。
   変数名も `main_worktree`→`base_worktree`、`old_main`→`old_base` に改める。
   出力の `SHIPPED\tmain\t(送る段なし)`・`NOTHING\t(main に無い…)`・`INVALID\tmain へ追い付けない` は
   枝名を埋め込む形にする
5. `main()` で `ledger.NoBaseBranch` を捕まえて `INVALID`（終了コード3）にする。
   呼び出しは遅延（`migrate` のように枝名を要らない道で落とさない）
6. `selftest_task.py`: `make_repo(..., base="main")`、`_no_merge_commits(repo, base="main")` にして
   既存のテストは既定値でそのまま通す。**`base="master"` で一式を通すテストを1本足す**
   （`status`→`new`→`claim`（feature 枝）→`done`→`ship`（本体が `master` を出している側へ ff）
   →本体で `ship`→`prune` まで）
7. `WORKFLOW.md` の「ファイル配置と CLAUDE.md」に任意行 `- 主ブランチ:` と順1〜4を書き、
   「送り出し」「`task` コマンドの参照」「1サイクル」などの `main` を「主ブランチ」に直す

## 注意

- `- 主ブランチ:` 行は**任意**。無いのが既定で、3行（検証コマンド・整形コマンド・ブランチ）の
  「行を消さない」規約には**入れない**（`MISSING_LINE` にしない）
- 正典 `skills/task-workflow/WORKFLOW.md` の「送り出し」「`task` コマンドの参照」にある `main` の
  記述は、枝名が可変になったことが分かる書き方に直す（既定が主ブランチであることは変えない）
- 調べて順1〜4のどれかが成り立たないと分かったら、`## 解くべき論点` に足して設計を変えてよい
- `selftest_task.py` の `test_ship_race_gives_up_after_three_tries` は、別スレッドが0.1秒おきに
  commit して取り合いを起こす形で**時間に依存して落ちることがあった**（枝名とは別件。`main` 固定の
  ままの HEAD でも全体実行で再現）。相手役を検証コマンド自体（rebase の直後・送る直前に本体を
  1コミット進める sh）に替えて決定的にした。`./check.sh` が機械の混み具合で落ちるのを止めるため

## 結果

- `ledger.base_branch()` が CLAUDE.md の任意行 `- 主ブランチ:` → `origin/HEAD` → `main`/`master`/`trunk` の順で決め、決まらなければ `INVALID`（3）。`task.py`・`ship.py` の git 引数はすべてこれ経由
- 検証コマンド: 202 pass / 0 fail（+23。`master` のリポジトリで一式を通すテストと決め方4通りのテストを追加）
- 振り返り: 完了条件に無い差分（ドラフト0件）
