## 目的

汎用化のあとで、あるリポジトリが新しい読み取りに合っているかを**機械で**確かめられるようにする。
移行を手順書で配らず、1コマンドの出力で済ませる。

## 完了条件

- `task config-doctor` があり、検査1つに1行のタブ区切りで次を出す:
  1. 主ブランチが何に決まったか（T-013 の順1〜4のどれで決まったか）
  2. 設定ファイルが `AGENTS.md` か `CLAUDE.md` か、両方に `## タスク運用` があって `INVALID` か
  3. `## タスク運用` の3行の在否と `- ブランチ:` の先頭語が語彙に当たるか
  4. 旧形式の残り（`develop/tasks.json`・`develop/progress.md`）があるか。あれば `task migrate` を案内
- 終了コードは 0（全部OK）／1（直すものがある。案内を出す）／3（`INVALID`）
- **何も書き換えない**（読むだけ。`--fix` は作らない）
- `selftest_task.py` に、OK のリポジトリ・旧形式が残っているリポジトリ・`AGENTS.md` と
  `CLAUDE.md` の両方に節があるリポジトリの3ケースがある
- `./check.sh` が通る

## 背景

適用中の5リポジトリを2026-09-26 に調べた結果:

| リポジトリ | 形式 | `- ブランチ:` の値 |
| --- | --- | --- |
| claude-skills | 新（`develop/task/` 2件） | `既定` |
| tsukumo | 新（32件） | `切らない（自分でブランチを切らない）` |
| Git-Bulk-Maestro | 旧（`develop/tasks.json`） | `作業ブランチを切る` |
| gitlab-watari-dori | 旧 | `切らない。直接 main にコミットする` |
| helm-yadokari | 旧 | `切らない。直接 main にコミットする` |

**5リポジトリとも主ブランチは `main`、`AGENTS.md` を置いているものは無い。** そのため T-013・
T-018・T-020 では既存リポジトリ側の書き換えは発生せず、移行は「壊れていないことの確認」だけになる。
だから `--fix` は要らず、点検だけでよい。

判定に使う部品はすでにある: 主ブランチは T-013 の `ledger.base_branch()`、設定ファイルの探索は
T-020 の関数、3行の点検は `skills/task-workflow/scripts/init.py:68` の `check_claude_md`、
旧形式の検出は `skills/task-workflow/scripts/legacy.py`（`task status` が `legacy_progress` 行を
出す仕組みがある）。**新しく判定を書き起こさず、これらを呼ぶ。**

## やること

いまのコードで前提を調べ直した。正典の節名は**すでに**「ファイル配置と設定ファイル（AGENTS.md →
CLAUDE.md の順）」に改称済み（T-020）で、背景・注意はこの新しい節名で読む。判定の部品は背景が
言うとおり実在する（`ledger.base_branch`〈`skills/task-workflow/scripts/ledger.py:97`〉、
`layout.find_config_file`、`init.py:68` の `check_claude_md`、旧形式の残りの検出は `task.py` の
`detect_format` と `legacy.migrate` が直接 `os.path.exists` で見ている `develop/tasks.json`・
`develop/progress.md`）。ただし2つだけ、既存の部品を「呼ぶだけ」では足りない差分がある:

- `ledger.base_branch()` は主ブランチ名だけを返し、**どの順で決まったかを外に出さない**。
  順1〜3の分岐そのもの（`_configured_base_branch` → `origin/HEAD` → `main`/`master`/`trunk`）は
  今のまま1箇所に残し、決めた順もその場で覚えて公開する2つ目の関数から読めるようにする
  （`base_branch()` の戻り値・呼び出し側の型は変えない）
- `init.check_claude_md()` は引数を取らず、カレントディレクトリ基準（`layout.find_config_file(".")`）
  で読む。`task.py` は `toplevel` を明示的に渡す作り（どこからで打ってもリポジトリの根で動く）
  なので、`root` 引数（既定 `"."` で `init.py` 自身の呼び方は変えない）を足して `toplevel` を渡す
- `task.py` の `main()` は `migrate` 以外のサブコマンドを `detect_format` の LEGACY/MISSING/INVALID
  で入口から止める（`if args.command != "migrate":`）。`config-doctor` の検査4は**この LEGACY 自体を
  検出して案内するのが仕事**なので、`migrate` と同じく入口の判定から外す

行う変更:

- `ledger.py`: 主ブランチの決め方の本体を `_resolve_base_branch(cwd) -> (名前, 順)` に括り、
  `base_branch()` はその1番目を返す薄い関数にする。2番目を返す `base_branch_order(cwd=None) -> int`
  を新設し、キャッシュ（`_base_branch_cache`）はタプルで持つ（`clear_base_branch_cache` は変えない）
- `init.py`: `check_claude_md(root: str = ".")` に直す（`layout.find_config_file(root)`・
  `os.path.exists(os.path.join(root, n))` に直すだけで判定は変えない）
- `task.py`: `import init` を足し、`cmd_config_doctor(toplevel)` を新設。4検査を必ず1行ずつ
  タブ区切りで出す（途中が INVALID でも残りの検査は続ける。呼び出し側が1回の実行で全体像を
  見られるようにする）:
  1. `base_branch\tOK\t<名前>\t順<N>` か、`ledger.NoBaseBranch`／`layout.ConfigConflict` を
     受けて `base_branch\tINVALID\t<理由>`
  2. `layout.find_config_file(toplevel)` を直接呼び、見つかった方の相対パスか `MISSING`／
     `ConfigConflict` を受けて `INVALID`
  3. `init.check_claude_md(toplevel)` の戻り値そのもの（`OK`／`MISSING_LINE`／`BAD_BRANCH`／
     `MISSING`／`NO_SECTION`／`INVALID`）を先頭語ごとそのまま出す
  4. `develop/tasks.json`・`develop/progress.md` の存在を直接見て、あれば
     `legacy\tFOUND\t<在るファイル>\ttask migrate --dry-run`、無ければ `legacy\tOK`
  終了コードは4検査の最悪値（INVALID があれば3、無くて何か直すものがあれば1、全部OKなら0）。
  `build_parser()` に `config-doctor` のサブパーサ（引数無し）を足し、`main()` の入口判定と
  ディスパッチにも `config-doctor` を足す
- `selftest_task.py`: `make_repo` は「## タスク運用」の3行のうち `- 整形コマンド:` を書かない
  （他のテストが見ないため）ので、`config-doctor` 用に3行そろった `CLAUDE.md` を直接書く
  小さなフィクスチャ関数を足し、OKのリポジトリ・`develop/tasks.json`/`develop/progress.md` が
  残っているリポジトリ・`AGENTS.md` と `CLAUDE.md` の両方に節があるリポジトリの3ケースを足す
- `./check.sh` を通す

## 注意

- 出力の形は `task status` と揃える（タブ区切り、1行1件）。人向けの段落を出さない
- `develop/direction.md` の在否は**新形式の目印**なので、検査4は `direction.md` が無いことを
  旧形式の証拠にしない（正典「ファイル配置と設定ファイル（AGENTS.md → CLAUDE.md の順）」）

## 結果

- `task config-doctor` が4検査を1行ずつ出す（主ブランチが決まった順・設定ファイルがどちらか・「## タスク運用」の3行・旧形式の残り）。読むだけで `--fix` は無く、終了コードは最悪値（0／1／3）
- 判定は書き起こさず既存の部品を呼ぶ。そのために `ledger` に `base_branch_order()`（決まった順を返す薄い関数。判定の本体は `_resolve_base_branch` 1箇所）と `init.check_claude_md(root)` の引数を足した
- 検証コマンド: 212 pass / 0 fail（+3。OK・旧形式の残り・AGENTS.md と CLAUDE.md の衝突の3ケース）
- 振り返り: 同じファイルを3回以上直した／受け入れでメインが直した（ドラフト2件）
